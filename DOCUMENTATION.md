## authentication

Custom, NOT a starter-kit scaffold. Auth field is **`username`**, not email.

- `app/Models/User.php` — `Authorizable` trait (Just A Gate), `#[Fillable(['name','username','email','password'])]`.
- `database/migrations/2026_07_11_082453_add_username_to_users_table.php` — adds `username` (string, unique) after `name`. **down() must `dropUnique(['username'])` before `dropColumn('username')`** — SQLite errors ("no such column after drop column") if you drop the column first while the unique index still references it.
- `app/Http/Requests/Auth/LoginRequest.php` — validates `username`+`password`, rate-limits via `RateLimiter` (5 attempts, keyed by `strtolower(username)|ip`), throws `ValidationException` with `auth.failed` / `auth.throttle` translation keys on failure.
- `app/Http/Controllers/Auth/AuthenticatedSessionController.php` — `create()` (GET /login view), `store()` (calls `$request->authenticate()`, regenerates session, redirects to `route('dashboard')` via `->intended()`), `destroy()` (logout: `Auth::logout()`, invalidate session, regenerate CSRF token).
- Routes in `routes/web.php`: `login` (GET/POST, `guest` middleware), `logout` (POST, `auth` middleware), `dashboard` (GET, `auth` middleware, inline closure view).
- Views: `resources/views/auth/login.blade.php`, `resources/views/dashboard.blade.php` — Tabler markup (`page`, `page-center`, `card card-md`, `form-control`, etc), each own full `<html>` document with `@vite(['resources/css/app.css','resources/js/app.js'])`.
- `lang/en/auth.php` published (was not present in Laravel 13 skeleton by default) — needed for `trans('auth.failed')`/`trans('auth.throttle')`.
- `database/factories/UserFactory.php` — generates `username` via `fake()->unique()->userName()`.
- Seeded user (via `DatabaseSeeder`): `username=test`, `email=test@example.com`, `password=password`.

## settings (key/value store)

- Table `settings`: `user_id` (nullable FK, `cascadeOnDelete`), `key` (string), `value` (text, nullable), unique on `(user_id, key)`. `user_id = null` means a global setting.
- Model `app/Models/Setting.php`: `Setting::valueFor(?int $userId, string $key, $default = null)` (user value → global value → default) and `Setting::setValue(?int $userId, string $key, $value)` (updateOrCreate, so re-setting a key updates the row instead of duplicating it).
- **Note on the unique index**: SQL treats `NULL <> NULL`, so a DB-level unique constraint alone would not stop two global rows sharing the same `key` if inserted via raw `create()`. Uniqueness in practice is guaranteed by always writing through `Setting::setValue()` (which does `updateOrCreate`) — never `Setting::create()` directly.
- `User` model exposes `$user->getSetting($key, $default)` / `$user->setSetting($key, $value)`, thin wrappers around the above scoped to `$this->id`.
- Per-user preferences (date format, language, number format, theme, theme base, theme color) are just entries in this table with a fixed key list defined in `config/preferences.php` — each entry is `['default' => ..., 'options' => [value => label]]`. `SettingsController::edit()`/`updatePreferences()` and `resources/views/settings/edit.blade.php` iterate `config('preferences')` generically, so adding a new preference is config + one form loop, no per-field code.
- `theme`/`theme_base`/`theme_color` are read directly in `layouts/app.blade.php` (`<html data-bs-theme="..." data-bs-theme-base="..." data-bs-theme-primary="...">`) on every page render (no caching). These map 1:1 onto Tabler's own theming attributes (see `node_modules/@tabler/core/scss/tabler-themes.scss`): `theme` is light/dark color mode, `theme_base` picks the gray/neutral scale (`gray`/`slate`/`zinc`/`neutral`/`stone`/`pink`), `theme_color` picks the accent color (`blue`/`azure`/`indigo`/`purple`/`pink`/`red`/`orange`/`yellow`/`lime`/`green`/`teal`/`cyan` — note the config key is `theme_color` but the HTML attribute is `data-bs-theme-primary`, matching Tabler's own naming). Only `theme` affects Bootstrap's light/dark CSS variables and the grid's `dark` flag (see below); `theme_base`/`theme_color` are purely cosmetic (gray scale + accent color) and don't need a `dark` equivalent. The sidebar `<aside>` always forces `data-bs-theme="dark"` regardless of the `theme` preference (a separate, intentional Tabler convention).
- `language` is applied per-request by `App\Http\Middleware\ApplyUserPreferences` (registered globally on the `web` middleware group in `bootstrap/app.php`), calling `App::setLocale()` before the request reaches the controller. Guests are skipped (`$request->user()` is null).
- `date_format`/`number_format` are stored but not yet wired into any output — no feature reads them yet. When building something that formats dates/numbers for display, resolve via `auth()->user()->getSetting('date_format', config('preferences.date_format.default'))` rather than hardcoding a format.

## translations (database-backed, custom — not Laravel's file-based i18n)

- Table `translations`: `key` (string, indexed), `language` (string, max 10), `value` (text), unique on `(key, language)`. No `user_id` — translations are global, not per-user (only which language to show is per-user, via the existing `language` setting).
- Model `app/Models/Translation.php`: `Translation::valueFor(string $key, ?string $language): ?string` — the only read path. It keeps a **static in-process cache keyed by language** (`private static array $cache`), populated on first lookup per language per request (one query per language, not per key), and flushed via `saved`/`deleted` model event hooks (`forgetCache()`) so writes are visible immediately without needing a fresh request.
- Global helper `t(string $key, array $replace = [], ?string $locale = null): string`, defined in `app/helpers.php` and autoloaded via Composer's `autoload.files` (registered in `composer.json` — re-run `composer dump-autoload` if the helper ever stops being found after editing `composer.json` by hand). **This is a project-specific helper, not a Laravel override** — `__()`/`trans()` are untouched and still read from `lang/`.
  - Resolution order: explicit `$locale` arg → `auth()->user()->getSetting('language')` (only if authenticated) → `config('app.locale')` (`APP_LOCALE`). If the resolved locale has no row for the key, it retries once against `config('app.locale')` (skipped if that's already what was tried). If still nothing, **returns the key itself unchanged** — same convention as Laravel's own missing-translation fallback, so a missing translation is visibly a raw key in the UI (easy to spot) rather than blank text.
  - Placeholder replacement mirrors `trans()`'s `:name` convention (`str_replace(':'.$search, ...)`), not full `MessageSelector` semantics (no pluralization, no nested arrays) — deliberately minimal, extend only if actually needed.
- **Every Blade view's static UI text uses `t()`, not `__()`.** All `__(...)` calls in `resources/views/**/*.blade.php` were mechanically swapped to `t(...)` (identical call signature — `t($key, $replace = [], $locale = null)` mirrors `__()`'s own signature exactly, so it was a safe find/replace: `sed -i 's/__(/t(/g'` per file). `lang/en/*.php` and Laravel's own `__()`/`trans()`/`@lang` are untouched and still used internally by validation/auth (`app/Http/Requests/Auth/LoginRequest.php`'s `trans('auth.failed')` etc) — don't migrate those, they're framework-internal, not app UI text.
- **rule (standing): use `t()` in new views wherever possible, and whenever you add a new `t('some string')` call, add its `it`/`en` entry to `database/seeders/TranslationSeeder.php`'s `$strings` array AND run `php artisan db:seed --class=TranslationSeeder` against whatever DB you're actively working against** — not just at install time. Skipping this means `t()` silently falls back to echoing the raw key, which is easy to miss since it's not an error.

### languages (runtime-managed, not a static config list)

- Table `languages`: `code` (string, max 10, unique), `name` (string). Source of truth for "what languages exist" — there is no hardcoded array anywhere.
- Model `app/Models/Language.php`: `Language::options(): array` returns `code => name` ordered by name, used everywhere a language dropdown is needed.
- Config `config/preferences.php` **no longer has a `language` key at all** — it's been replaced by the `preferences()` helper (`app/helpers.php`), which returns `config('preferences')` with a `language` entry injected dynamically: `['default' => config('app.locale'), 'options' => Language::options()]`. **Always call `preferences()`, never `config('preferences')` directly**, anywhere the full preference set (including language) is needed — `SettingsController`, `UpdatePreferencesRequest`, `resources/views/settings/edit.blade.php` all do this. `date_format`/`number_format`/`theme` are unaffected, still plain config.
- Admin CRUD (add/list/delete only, no rename): `app/Http/Controllers/Admin/LanguageController.php`, routes `admin/languages` (`index`/`store`/`destroy` only — `Route::resource(...)->only([...])`), single combined view `resources/views/admin/languages/index.blade.php` (list + inline "add" form, no separate create page — the list is short enough that a dedicated page would be overkill). Menu entry "Lingue" in `layouts/admin.blade.php`.
- **Deleting a language is refused if any `Translation` row still references its code** (`Translation::where('language', $code)->exists()` check in `destroy()`) — prevents silently orphaning translated content. There's no rename/update endpoint at all: changing a language's `code` after translations exist against it would orphan them the same way, so it's simply not exposed; delete + re-add if you really need to change a code.
- `LanguageSeeder` seeds `it`/`en`, called from `DatabaseSeeder` **before** `TranslationSeeder` (translations reference language codes conceptually, though the FK isn't enforced at the DB level — `language` is a plain string column, not a foreign key to `languages.code`, so a `Translation` row can technically reference a language that's since been deleted; the UI just won't show/manage it anymore since it drops out of `Language::options()`).

## admin CRUD (Users / Roles / Translations / Languages)

- **Translations use a pivoted admin UI, not a flat "one row per (key, language)" CRUD.** The `/admin/translations` grid shows **one row per key**, with one column per language (from `Language::options()`), populated by `TranslationController::data()`.
  - **Why not `EloquentSource` here:** Laraccoon's `EloquentSource` (used by Users/Roles/every other grid in this app) operates on a query builder and applies filters/sort/pagination assuming **one row per underlying record** — it has no concept of pivoting many rows (one per language) into one output row per key. `data()` therefore builds the `{data, total}` response by hand: get the distinct, paginated, optionally-search-filtered `key` values first, then `groupBy('key')` the matching `Translation` rows and flatten each group into `['id' => ..., 'key' => ..., 'it' => ..., 'en' => ..., ...]`. The `id` field is just the first underlying `Translation` row's id for that key — used purely as a URL anchor for the Modifica/Elimina row actions, not a meaningful identifier on its own.
  - `create()`/`store()`: one `key` input + one value field per language (`values[it]`, `values[en]`, ...). `StoreTranslationRequest` requires the key not already exist at all (`Rule::unique('translations', 'key')` — since the same key legitimately repeats across language rows, this only makes sense for the "this key is brand new" case) and that **at least one** language value is filled in (custom `withValidator()` check, since `values.*` are individually `nullable`).
  - `edit($translation)`/`update()`: `$translation` is only used to resolve `$translation->key` (route-bound by an arbitrary single row's id, see above) — the form then shows/saves **every** language's value for that key at once. Leaving a language's field blank on update **deletes** that language's row for the key (lets you "un-translate" a language without deleting the whole key); filling one in upserts it. The `key` itself is **not editable** on this form (rename-by-editing isn't supported, same reasoning as languages above) — the field is rendered `readonly`.
  - `destroy($translation)`: deletes **every** row sharing `$translation->key` — i.e. the whole key, across all languages, not just one row.
- Routes: `routes/web.php`, inside `Route::prefix('admin')->name('admin.')->middleware('acl')->group(...)`. Each resource with a `data()` endpoint registers `Route::get('{resource}/data', ...)` **before** `Route::resource(...)` so it isn't swallowed by the `{model}` wildcard.
- The `acl` middleware (`Fazzinipierluigi\JustAGate\Middleware\AclCheck`, aliased from `config('acl.middleware')`) derives the required permission key from the controller/action: `Admin\UserController@index` → `user.index` (strip namespace, strip `Controller`, lowercase, `@` → `.`). Every action — including the `data` endpoint — has its own key. A role needs each key granted individually for granular access; `is_admin` roles bypass all of it.
- `admin.access` (checked in the base menu, see above) is a separate, coarser key not tied to any one controller action — it only gates the sidebar link's visibility, not an actual route. Not pre-created anywhere; only matters once a non-admin role needs the link visible (grant via `permission:create admin.access "..."` + `permission:assign admin.access {role}`).
- Controllers: `app/Http/Controllers/Admin/{User,Role,Translation,Language}Controller.php`. Each has `index()` (renders the grid/list page), `create()/store()`, `edit()/update()`, `destroy()` (User/Role/Translation only — Language has no edit); User/Role/Translation additionally have `data()` (JSON, either via `EloquentSource` or, for Translation, the manual pivot above).
- Business rules: `UserController::destroy()` refuses to let a user delete their own account (compares `$user->id` to `$request->user()->id`). `RoleController`: system roles (`is_system=true`, e.g. `admin`) can't be deleted. `LanguageController::destroy()`: refused if any `Translation` still uses that language.
- **No standalone Permissions CRUD/page exists** — deliberately removed. `Fazzinipierluigi\JustAGate\Models\Permission` rows are only ever created via CLI (`permission:create`/`permission:import`). The Role permissions screen (`admin/roles/{role}/permissions`) only assigns existing permissions to a role — it never creates new `Permission` rows. Don't re-add an `Admin\PermissionController`/`admin/permissions/*` routes/views/menu entry unless explicitly asked again — this was built once and intentionally rolled back.
- `DatabaseSeeder` creates/fetches the `admin` role (`slug=admin, is_admin=true, is_system=true`) and assigns it to the seeded `test` user, then calls `LanguageSeeder` and `TranslationSeeder` in that order — without this, a fresh `db:seed` wouldn't grant the seeded user access to `/admin/*`, show the Amministrazione link, or populate any languages/translations.
- **`roles.slug` has an app-added unique DB constraint** (`database/migrations/2026_07_11_130459_add_unique_index_to_roles_slug.php`, dropping the vendor migration's plain non-unique index and replacing it with `unique('slug')`). The vendor `create_roles_table` migration only declares `$table->string('slug')->index()` — plain, non-unique — so nothing at the DB level stopped two "admin" rows from existing simultaneously (this actually happened once in this project's dev DB: two `slug=admin` rows split across `role_user` pivot rows, found and fixed by hand — reassign the pivot rows to one row, delete the duplicate, then add the constraint). Form-level `unique:roles,slug` validation is not enough on its own; always keep the DB constraint as the real guarantee.

### gotchas hit while building translations/languages

- **`Translation::upsert()` is a query-builder bulk operation — it does not fire Eloquent's `saved`/`deleted` model events**, so `Translation::forgetCache()` (which those events normally trigger) never runs automatically. `TranslationSeeder` calls `Translation::forgetCache()` itself right after the `upsert()` call to compensate. Any other bulk/raw write path (`DB::table('translations')->...`, another `upsert()`, mass `update()`/`delete()` via the query builder — as used inside `TranslationController::update()`'s "clear a language" branch, which uses a query-builder `delete()`, not a model `delete()`!) needs the same explicit `forgetCache()` call, or must rely on a *different* row's save/delete in the same request to incidentally flush it. Only single-model `create()`/`update()`/`delete()` invalidate the cache on their own.
- **Test-suite gotcha:** `Translation::$cache` is a `private static array`, so it survives across **all** test cases run in the same PHPUnit/Pest process (Feature and Browser tests each run in one process). Fixed by resetting it globally in `tests/Pest.php`: `->afterEach(fn () => Translation::forgetCache())` chained onto both the `Feature` and `Browser` `pest()->extend(...)` calls. Not a production concern under normal per-request PHP execution (fresh process = empty static array) — only bites long-lived processes (Octane, the Pest test runner) or code paths bypassing Eloquent events.
- **Test-suite gotcha:** the `languages` table starts **empty** in every isolated test (no seeder runs automatically under `RefreshDatabase`/`DatabaseMigrations`) — any test that renders a translations/settings-preferences view, or posts to `.../preferences`, needs at least `it`/`en` to exist, or language `<select>`s render with zero options and `Rule::in([])` rejects every submitted value. Use the `seedLanguages()` global test helper (`tests/Pest.php`, alongside `adminUser()`) rather than hand-rolling `Language::create(...)` in every test.
- **Blade `@json(...)` directive parsing breaks on a complex inline expression mixing `->map(fn ($x) => [...])` (arrow function returning an array literal) directly inside the directive's parens** — got `Unclosed '[' on line N does not match ')'` compiling `resources/views/admin/translations/index.blade.php`. Fix: compute the value in a preceding `@php ... @endphp` block into a plain variable, then `@json($thatVariable)`. Keep `@json()`'s argument to a simple variable/property access; don't nest non-trivial closures/array literals directly inside it.
- **A `confirm()` dialog on a plain server-rendered form (`onsubmit="return confirm(...)"` present in the HTML from the very first page load) genuinely blocks Dusk in headless Chrome and needs explicit `->waitForDialog()->acceptDialog()`** — this contradicts the earlier-documented assumption (see the gotcha list below) that headless Chrome always auto-resolves `confirm()`. The distinction that actually matters: the delete buttons rendered by **Raccoon Tables' JS `render()` callback** (Users/Roles grids — HTML string injected via the grid library, not present in the initial server response) resolve their `confirm()` without any dialog handling needed; the delete button on the **plain server-rendered** `admin/languages/index.blade.php` table (no JS grid involved) did not, and needed `waitForDialog()`/`acceptDialog()` (`tests/Browser/Admin/LanguagesTest.php`). If a new confirm-guarded action doesn't behave as expected in Dusk, try both approaches rather than assuming either one universally.

## ACL (Just A Gate)

- Config: `config/acl.php`. Keys: `middleware` (default `'acl'`), `additional` (manual `key => name` map), `role_user_creation` (bool, auto-generates a `user.create.role_{slug}` permission per role), `clean_permission` (bool, deletes stale permissions on import), `assign` (`permission_key => [role_slug, ...]` auto-assignment map), `translate` (`permission_key => display name` override).
- Tables (package migrations, not in this repo's `database/migrations`, loaded from vendor): `roles`, `permissions`, `permission_role`, `role_user`.
- Models: `Fazzinipierluigi\JustAGate\Models\{Role,Permission,PermissionRole,RoleUser}`.
- Artisan commands: `permission:init` (first run — migrates + creates `admin` role), `permission:create {key} {name?}`, `permission:assign {key} {role}`, `permission:import` (bulk regenerate from `config/acl.php` + route scan + role scan, applies `assign`/`clean_permission`/`translate`).
- Gating Livewire: `#[Fazzinipierluigi\JustAGate\Attributes\RequiresPermission('key')]` on a class (checked every lifecycle) or a method (checked only on that action).
- `User` model must `use Authorizable` (already wired).

## layout & menus

- `resources/views/layouts/app.blade.php` — single shared shell for every authenticated page: `.page` > fixed vertical `<aside class="navbar navbar-vertical navbar-expand-lg" data-bs-theme="dark">` (Tabler's vertical-nav layout is fixed by default, no extra CSS needed) + `<header class="navbar ... sticky-top">` + a Tabler `.page-header` (title/breadcrumb/buttons, see below) + `.page-wrapper > .page-body > .container-fluid` for `@yield('content')`. `@yield('menu')` inside the aside is filled by whichever of the two menu layouts below is used.
- **Page header slots — use these instead of hand-rolling a `.page-header`/`.page-title` block in a view's `@section('content')`.** The layout renders the header itself from three sections:
  - `@section('title', 'Page Name')` — required, also feeds the `<title>` tag. Every view already sets this.
  - `@section('breadcrumb') <li class="breadcrumb-item">...</li> ... @endsection` — optional (`@hasSection`-gated); the home icon is always prepended by the layout, don't add it yourself. List views render one `breadcrumb-item active` for themselves; create/edit views render a link back to the index plus an active item for themselves (see `resources/views/admin/users/{index,create,edit}.blade.php` for the pattern — same in `roles`/`permissions`).
  - `@section('buttons') <a class="btn btn-primary" ...>...</a> @endsection` — optional (`@hasSection`-gated), right-aligned action button(s) (e.g. "Nuovo utente"). **Hard design rule: every save button and page-level action button goes here — never in a `form-footer` at the bottom of a card.** Only *contextual* actions (a row's Modifica/Elimina inside a list/datatable) are exempt and stay where they are. For a create/edit form, this means the `<form>` gets an `id` and the submit button lives in `@section('buttons')` as `<button type="submit" form="that-id" class="btn btn-primary">` — physically outside the `<form>` element, associated via the HTML `form=` attribute (works identically to a button inside the form). See `admin/entities/create.blade.php`/`edit.blade.php`, `admin/roles/*`, `admin/translations/*`, `admin/users/*`, `admin/languages/index.blade.php`, `settings/edit.blade.php` for the pattern applied throughout the app. A page with two independent forms (e.g. `settings/edit.blade.php`'s personal-settings card + preferences card, `admin/languages/index.blade.php`'s language list + add-language form) puts **multiple buttons in the header**, each `form=`-wired to its own form id — there's no exception for multi-form pages. A conditionally-rendered form (e.g. `admin/entities/visibility.blade.php`, which only shows a form when roles exist) wraps its `@section('buttons')` in the same `@if` so the button doesn't appear when the form doesn't. Secondary same-page navigation links that used to sit next to a save button in the old form-footer (e.g. "Progetta struttura" next to an entity's save, "Gestisci permessi" next to a role's save) move to the buttons area too — they're "tasti azione", not contextual list actions. `auth/login.blade.php` is out of scope (doesn't extend `layouts.app`, no buttons yield, different centered-card UX).
  - Views with no natural breadcrumb/buttons (dashboard, personal settings) just omit those two sections — nothing to do beyond `@section('title', ...)`.
- `resources/views/layouts/base.blade.php` (`@extends('layouts.app')`) — "Dashboard" link + bottom-anchored (`.mt-auto`) "Amministrazione" link. The admin link is wrapped in `@can('admin.access') ... @endcan`.
- `resources/views/layouts/admin.blade.php` (`@extends('layouts.app')`) — Utenti / Ruoli / Traduzioni links + "back to dashboard" link. No standalone "Permessi" menu entry/page — see "admin CRUD" below.
- Top navbar right-side cluster order: notifications bell (`data-testid="notifications-toggle"`, static empty dropdown) → user dropdown (`data-testid="user-menu-toggle"`, shows name + comma-joined role names via `auth()->user()->getRoles()->pluck('name')->join(', ')`, dropdown has Impostazioni + Logout).
- `data-testid="*"` attributes are sprinkled through the layout/menu markup specifically so Dusk tests can target elements without depending on Tabler's own CSS classes (which could change with a Tabler upgrade). Keep adding `data-testid` to new interactive elements you want to test.
- **`@can`/`@endcan` in Blade is Just A Gate's, not Laravel's.** `JustAGateServiceProvider::bootBladeDirectives()` does `Blade::if('can', fn ($ability) => Auth::user()->can($ability))`, overriding the framework directive. This means `@can('some.key')` correctly calls Just A Gate's `User::can()` (role/permission based). **Laravel's `can:` route middleware and `Gate::authorize()`/`$this->authorize()` do NOT go through this override** — they use Laravel's own `Gate` facade, which has no abilities registered for Just A Gate keys and will always deny. For route-level protection use Just A Gate's own `acl` middleware (see below), never `can:`.

### role-specific rules (on top of the generic admin CRUD rules above)

- **The `admin` role (`is_admin=true`) is fully locked down** — not just its slug. `RoleController::edit()`/`editPermissions()` redirect back to the index with a flash `error` instead of rendering (GET), and `update()`/`updatePermissions()` do the same instead of saving (POST/PUT) whenever `$role->is_admin` is true; this is checked at the top of all four methods, not just in a form. `resources/views/admin/roles/index.blade.php`'s actions-column `render()` also hides the Modifica/Permessi buttons when `params.item.is_admin` (mirroring the existing `is_system` check that already hides Elimina) — but the controller-side checks are the actual guarantee, the hidden buttons are just UX; hitting the routes directly (e.g. `PUT admin/roles/{adminRoleId}`) is still blocked.
- **Role slugs are auto-generated from the name on create**, never typed by hand: `RoleController::store()` computes `Str::slug($name)` and appends `-2`, `-3`, ... until unique (`uniqueSlug()` private method) — `StoreRoleRequest` has no `slug` rule at all. The create form (`resources/views/admin/roles/create.blade.php` → `_form.blade.php`) has no slug field; `_form.blade.php`'s slug block is guarded by `@if ($role)` so it only appears on the edit form (where the slug is still editable for non-system, non-admin roles, per the existing `is_system` lock).
- `RoleController` additionally has `editPermissions()/updatePermissions()` (routes `admin/roles/{role}/permissions`, keys `role.editpermissions`/`role.updatepermissions`) — the **only** place a role's permissions are assigned; `RoleController::store()/update()` only ever touch `name`/`slug`.

### Just A Gate `syncPermissions()` expects **keys**, not IDs

`Fazzinipierluigi\JustAGate\Models\Role::resolvePermission()` accepts a `Permission` instance or a **string key** (`Permission::where('key', $permission)->firstOrFail()`) — there is no `int`-as-id branch (unlike `resolveRole()`, which does accept `Role|string|int`). Passing permission **IDs** to `syncPermissions()` throws `ModelNotFoundException` ("No query results for model [Permission]") because it tries to look up a permission whose `key` equals the numeric id string.

Consequence: `resources/views/admin/roles/permissions.blade.php`'s checkboxes use `value="{{ $permission->key }}"` (not `->id`), `UpdateRolePermissionsRequest` validates `permissions.*` against `exists:permissions,key` (not `,id`), and `RoleController::updatePermissions()` passes the raw request array straight through to `syncPermissions()` — no id-to-model resolution needed. Contrast with `User::syncRoles()` (`Authorizable` trait), which does accept role IDs directly.

## Raccoon Tables + Laraccoon Datasource integration

- `resources/js/app.js` imports `RaccoonGrid` from `raccoon-tables` and exposes it as `window.RaccoonGrid` — each admin index view instantiates its own grid via a plain inline `<script>` (no per-page Vite entrypoints), e.g. `new window.RaccoonGrid({ ... }).render('#users-grid')`.
- **`serverAdapter` defaults to `method: 'POST'`** (per Raccoon Tables' own docs), but our data routes are `Route::get(...)`. Left as default this 405s (`Method Not Allowed`). Fix: every grid config sets `serverAdapter: { url: ..., method: 'GET' }` explicitly. (Alternative considered and rejected: accepting POST too via `Route::match(['get','post'], ...)` — would need CSRF header wiring for no real benefit, since these endpoints are read-only.)
- **`EloquentSource::apply()` returns an empty result set if the request has no `limit` param** (`$limit = (int)($params['limit'] ?? 0); if ($limit <= 0) $this->filtered_dataset->take(0);`). Raccoon Tables' own client always sends `start`/`limit` in real usage, so this only bites manual/test requests hitting `*/data` directly — always pass `?start=0&limit=25` (or similar) when calling these endpoints outside the actual grid (see Pest tests in `tests/Feature/Admin/*ControllerTest.php`).
- **Global search requires `$search_fields` passed explicitly** to `EloquentSource::apply($query, $request, $field_map, $search_fields)` — the grid's `searchBar: true` sends a `globalSearch` param regardless, but the backend silently ignores it unless `$search_fields` lists which columns to search (e.g. `['name', 'username', 'email']` for users). Without this, typing in the search box returns unfiltered results.
- Row actions (Modifica/Elimina) are rendered by our own `render` callback on an `actions` column — plain HTML strings (an `<a>` and a `<form>` with a hidden `_method=DELETE` + `_token` from `window.CSRF_TOKEN`, exposed globally in `layouts/app.blade.php`). Not a Raccoon Tables feature — just template strings we own.
- Raccoon Tables DOM class names used by Dusk tests (stable, taken from the shipped source, not guessed): `.rt-search-bar-input` (the search box), `.rt-row` / `.rt-cell` (grid rows/cells), `.rt-wrap.rt-dark` (root wrapper gains `rt-dark` when `dark: true`).
- **Grid theme follows the logged-in user's `theme` preference**: every grid config sets `dark: @json(auth()->user()->getSetting('theme', config('preferences.theme.default')) === 'dark')` alongside `theme: 'tabler'`. Keep this line whenever adding a new grid — it's not automatic, each `RaccoonGrid` instantiation needs its own `dark` flag.

## testing infrastructure

Two suites, deliberately separated because **SQLite `:memory:` cannot be shared across processes** (the Dusk browser drives the app over real HTTP, hitting a separate PHP process from the one running the test assertions).

### Pest (Feature/Unit)

- Config: `phpunit.xml`. Forces `DB_DATABASE=:memory:`, `SESSION_DRIVER=array`, `CACHE_STORE=array` — fast, isolated, in-process only.
- `tests/Pest.php`: `pest()->extend(TestCase::class)->in('Feature')` (RefreshDatabase commented out — tests that hit the DB opt in per-file via `uses(RefreshDatabase::class)`, see `tests/Feature/AuthenticationTest.php`).
- Run: `composer test` (= `php artisan config:clear && php artisan test`).

### Dusk (Browser)

- Config: `phpunit.dusk.xml.dist` — separate phpunit config, `testsuite Browser -> tests/Browser`, intentionally has **no `<php><env>` overrides** so it inherits whatever `.env` is active at run time.
- `.env.dusk.local` — committed (not secret), points `DB_DATABASE` at an absolute path `database/testing.sqlite` (gitignored via `database/.gitignore` `*.sqlite*`), `SESSION_DRIVER=database`, `CACHE_STORE=database`, `BCRYPT_ROUNDS=4`, `QUEUE_CONNECTION=sync`, `MAIL_MAILER=array`, `APP_URL=http://127.0.0.1:8000`.
- `tests/Pest.php`: `pest()->extend(DuskTestCase::class)->use(DatabaseMigrations::class)->in('Browser')`.
  - **Gotcha (hit once, fixed):** the `use Tests\DuskTestCase;` / `use Illuminate\Foundation\Testing\DatabaseMigrations;` import statements MUST appear textually before the `pest()->extend(...)` line that references the short class names. Pint's `ordered_imports`/`fully_qualified_strict_types` fixers will happily move `use` statements below the code that references them (valid plain PHP, since `use` is compile-time) — but Pest's own file loader is sensitive to source order and throws `Pest\Exceptions\TestCaseClassOrTraitNotFound` if the import comes after the reference. Keep all `use` statements at the top of `tests/Pest.php`.
- `scripts/dusk.sh` — orchestrates a full Dusk run:
  1. backs up `.env` to `.env.backup.dusk`, copies `.env.dusk.local` over `.env`
  2. `php artisan migrate:fresh --force` (against the dusk sqlite file)
  3. starts `php artisan serve --host=127.0.0.1 --port=8000` in background, polls `/login` until it responds
  4. runs `php artisan dusk "$@"`
  5. `trap ... EXIT` always kills the serve process and restores the real `.env`, even on failure/Ctrl-C.
- Composer scripts: `composer test:dusk` (= `bash scripts/dusk.sh`), `composer test:all` (= `@test` then `@test:dusk`).
- System requirement: Chromium/Chrome binary must be installed (`chromium` via pacman on this box). `laravel/dusk`'s bundled ChromeDriver binary alone is not sufficient — it drives an actual browser binary that must exist on `$PATH`.
- Dusk tests must use `DatabaseMigrations` (or `DatabaseTruncation`), never `RefreshDatabase` (transactions don't cross the HTTP-request process boundary).
- Prefer `waitForLocation(...)` / `waitForText(...)` over immediate `assertPathIs(...)`/`assertSee(...)` right after `->press(...)` — a redirect race causes intermittent `stale element reference` errors otherwise (hit and fixed in `tests/Browser/LoginTest.php`).
- **Native `confirm()` dialogs (e.g. the delete buttons' `onsubmit="return confirm(...)"`) resolve immediately in this headless Chrome setup (`--headless=new`) — `waitForDialog()`/`acceptDialog()` never see an actual dialog and just time out.** Don't use Dusk's dialog-handling methods for these; just act as if the confirm always resolved to `true` and wait for the resulting navigation/text directly (see `tests/Browser/Admin/UsersTest.php`).
- When a page/grid shows a value the currently-logged-in user's own data also contains (e.g. the admin's name is always in the top navbar), scope `waitUntilMissingText()`/similar assertions to a specific container (`->within('#some-grid', fn ($el) => $el->waitUntilMissingText(...))`) — asserting against the whole page will never succeed if that same text is always present elsewhere on screen.

## entities (dynamic module builder)

Data model only so far (Phase 1 of the Entity builder — install engine, admin UI, visibility enforcement, and frontend CRUD land in later phases; this section grows with them).

- Goal: let an admin design a custom data module ("Entità") — tabs → cards → fields — which, once installed, gets a real dedicated SQL table, CRUD permissions, and a menu entry. "System entities" (pre-installed at app install) are a **future** step, not built yet.
- Tables (app migrations `database/migrations/2026_07_11_1534{10..14}_*`, run in that exact numeric order — they were all generated by `make:migration` in the same minute and had to be renamed to enforce FK dependency order: `entities` → `entity_tabs` → `entity_cards` → `entity_fields` → `entity_role_visibility`):
  - `entities`: `name`, `slug` (unique), `table_name` (unique, meant to hold `entity_{slug}`), `icon` (nullable Tabler icon class), `is_system`, `is_installed`.
  - `entity_tabs`: `entity_id` FK cascade, `name`, `position`.
  - `entity_cards`: `entity_tab_id` FK cascade, `name`, `position`.
  - `entity_fields`: `entity_card_id` FK cascade, `name`, `column_name`, `type` (string, backed by `App\Enums\EntityFieldType`), `options` (json, only meaningful for `Select`), `relation_target_type`/`relation_target` (nullable, only for `Relation`), `required`, `default_value`, `position`. **Unique constraint is `(entity_card_id, column_name)`, not entity-wide** — `entity_fields` has no direct `entity_id` column (only reachable through `entity_card_id → entity_tab_id → entity_id`), so true entity-wide column-name uniqueness must be enforced in application/validation code (Phase 2), not at the DB level.
  - `entity_role_visibility`: `entity_id` FK cascade, `role_id` FK cascade → `roles.id` (vendor just-a-gate table), `level` (string, backed by `App\Enums\EntityVisibilityLevel`), unique `(entity_id, role_id)`.
- Models `app/Models/{Entity,EntityTab,EntityCard,EntityField,EntityRoleVisibility}.php`, same `#[Fillable]`-attribute convention as `Setting`/`Translation`/`Language`. **`EntityRoleVisibility` needs an explicit `protected $table = 'entity_role_visibility'`** — Eloquent's automatic pluralization turns it into `entity_role_visibilities`, which doesn't match the migration; every other model here follows Laravel's default pluralization fine, this one is the exception.
- `Entity::allFields()` walks `tabs.cards.fields` (eager-load them first) and flattens to one collection — used wherever every field across the whole entity is needed (e.g. rendering the generic form later).
- Enums live in `app/Enums/` (first use of this directory in the app) — `EntityFieldType` (12 cases: Checkbox/String/Select/IntegerNumber/DecimalNumber/Textarea/RichText/Relation/Date/Time/DateTime/ColorPicker, each with a `label()` and `options()` static helper for `<select>`s), `EntityVisibilityLevel` (OwnOnly/OwnManageOthersRead/OwnManageOthersEdit/Full, same `label()`/`options()` pattern), `EntityRelationTargetType` (Entity/Model, no label — internal only).
- `config/entities.php` — first config file for this feature: `relatable_models` (FQCN => label map, currently just `User::class => 'Utente'`), the whitelist of system Eloquent models a `Relation` field can target besides other Entities. Same shape/spirit as `config/preferences.php`.
- This is the **first JSON column** (`entity_fields.options`) and the **first enum casts** in the app — no prior precedent existed for either; both use plain `casts()` method overrides like every other model here (no `$casts` property).

### admin: entity metadata CRUD + tab/card/field builder (Phase 2)

- `App\Http\Controllers\Admin\EntityController` — same shape as `RoleController`: `index`/`data` (`EloquentSource`, search on `name`/`slug`), `create`/`store` (slug auto-generated from `name` via the same `Str::slug` + numeric-suffix pattern as `RoleController::uniqueSlug()`, **never user-editable, and not just locked for system rows — every entity's slug is permanently fixed at creation** since `table_name` is derived from it once and the real dynamic table will be named after it from Phase 3 onward), `edit`/`update` (name/icon only), `destroy` (refused if `is_system` **or** `is_installed` — mirrors `RoleController`'s `is_system` guard, extended one step further since deleting an installed entity would orphan its live table/permissions once Phase 3 creates them). `store()` redirects straight into the builder (`admin.entities.builder.edit`), not the index — designing the structure is the natural next step after naming an entity.
- `App\Http\Controllers\Admin\EntityBuilderController` (`admin/entities/{entity}/builder`, GET/PUT) — the tab→card→field designer. `update()` **replaces the entity's entire tab/card/field tree in one transaction** (`$entity->tabs()->delete()`, cascading to cards/fields via the FK `cascadeOnDelete()`, then recreates everything from the submitted payload) — there is no id-based diffing. This is deliberately simple and safe *only because* `UpdateEntityBuilderRequest::withValidator()` refuses the request outright (error on the `tabs` key) whenever `$entity->is_installed` is true, **before** the controller ever runs — so the destructive rebuild can never touch a structure whose real SQL table already exists. Editing an installed entity's structure (add-only, per the original design intent) is deferred until Phase 3 builds `EntitySchemaBuilder`/`EntityInstaller` and the builder can be taught to call `addColumn()` for genuinely new fields instead of rebuilding blind.
- **The submitted tree's array keys are arbitrary, disposable tokens — not database ids.** Blade renders existing rows keyed by their real DB id (`tabs[{{ $tab->id }}][...]`) purely so the ids are stable/debuggable in the DOM; new rows added client-side get JS-generated tokens like `tnew1`/`cnew3`/`fnew2`. The controller ignores whatever key each row arrives under and just does `array_values($request->input('tabs', []))` at each level, using **loop position** as the `position` column — PHP preserves insertion order on associative arrays, and browsers submit form fields in DOM order, so this reproduces the on-screen order without needing explicit position inputs or id round-tripping at all. `tabs.*.id`/`cards.*.id`/`fields.*.id` are validated as `nullable integer` but never read.
- Validation (`UpdateEntityBuilderRequest`): ≥1 tab, each tab ≥1 card, each card ≥1 field (the "tab→card→field" nesting the client described is enforced structurally, not just at the top level). `withValidator()` additionally checks, across the *whole* submitted tree regardless of which card a field is under: `column_name` isn't one of `id/user_id/created_at/updated_at/deleted_at` (reserved for the dynamic table's own bookkeeping columns, see Phase 3), and `column_name` is unique **entity-wide** — the DB only enforces uniqueness per-card (`entity_fields` has no direct `entity_id` column, see Phase 1 notes above), so this app-level check is the real guarantee for cross-card collisions. `Select` fields require non-empty `options`; `Relation` fields require a non-empty `relation_target`.
- **`options` and `relation_target` use compact single-input encodings instead of extra structured inputs**, to keep the repeater's DOM flat: `options` is a textarea, one `key:Label` pair per line, parsed by `EntityBuilderController::parseOptions()` (`preg_split('/\R/', ...)`, splits each line on the first `:`) into the assoc array actually stored in `entity_fields.options`. `relation_target` is a single `<select>` whose option values are pre-joined as `entity:{slug}` or `model:{FQCN}` (built by `EntityBuilderController::relationTargetOptions()` from every *other* `Entity` plus `config('entities.relatable_models')`); `relationTargetType()`/`relationTarget()` just `explode(':', ..., 2)` that string back apart before saving. No separate hidden "target type" field or JS toggle needed for that half.
- **New repeater pattern (first of its kind in the app)**: `resources/js/entity-builder.js`, a standalone Vite entrypoint (added to `vite.config.js`'s `input` array — **run `npm run build` after pulling changes that touch it, or any Dusk/manual test hitting the builder page 500s with `Unable to locate file in Vite manifest`**) loaded via a page-local `@vite('resources/js/entity-builder.js')` call at the bottom of `builder.blade.php`'s `@section('content')`, not through the shared `layouts/app.blade.php` head. It works by reading a `<template>` element's `.innerHTML` as a **plain string**, doing a literal token replacement (`__TAB__`/`__CARD__`/`__FIELD__` → a freshly minted `tNNN`/`cNNN`/`fNNN` token), then parsing the result via a throwaway `<div>.innerHTML` and appending `.firstElementChild` — deliberately avoiding `cloneNode()` + manual attribute rewriting, since string substitution across a whole nested `name="tabs[__TAB__][cards][__CARD__]..."` attribute is far simpler than walking the cloned subtree. There are three independent `<template>` tags (`#tab-template`, `#card-template`, `#field-template`), each rendered server-side from the **same Blade partials used for real data** (`admin/entities/_tab.blade.php`, `_card.blade.php`, `_field.blade.php`, each accepting a nullable model + token(s) so one partial serves both the "existing data" `@foreach` and the "empty template" call site) — this guarantees the JS-cloned markup and the server-rendered markup never drift apart. Row deletion is just `element.closest('.repeatable-row').remove()`; there's no counterpart "restore" and no confirm dialog (low-stakes client-side-only state until submit). A field row's Select-only `options` textarea and Relation-only `relation_target` select are shown/hidden via a `.field-type-select` `change` listener (delegated on the form, so it works for dynamically-added rows too) toggling a `.d-none` class — and the same sync runs once on `DOMContentLoaded` over every pre-existing `.field-type-select`, since existing rows' visibility can't rely on a `change` event that never fires for them.
- When `$entity->is_installed` (not reachable yet from the UI — no install action exists until Phase 3, but the guard is already wired defensively), `builder.blade.php` wraps the whole tree in `<fieldset disabled>` and hides the submit button (`@unless ($entity->is_installed)`), so the page is inert even before the server-side rejection would kick in.
- New `config('entities.relatable_models')` keys and any new field type added to `EntityFieldType` need a matching entry point in `_field.blade.php`'s target/options UI — nothing auto-discovers new cases.

### installer: dynamic table + permissions + menu (Phase 3)

- `App\Services\EntitySchemaBuilder` — the **only place in the app that runs `Schema::` calls outside `database/migrations`**. `create(Entity $entity)` builds the entity's real table: `id`, `foreignId('user_id')->constrained()->cascadeOnDelete()` (the record owner, required — every dynamic table has one, it's what Phase 4's visibility levels scope against), one column per field via the type map below, then `timestamps()`. `addColumn(Entity, EntityField)` (`Schema::table`, single column) exists for adding a field to an *already-installed* entity later, but nothing calls it yet — `EntityBuilderController` still refuses to touch an installed entity at all (Phase 2's stricter-than-planned lockdown), so this method is currently dead code reserved for when that gets revisited. `dropTable()` is a plain `Schema::dropIfExists()`.
  - Type → column: `Checkbox`→`boolean` default false; `String`/`Select`→`string(255)` nullable (Select stores the chosen option's key, its labels live in `entity_fields.options`, not the DB); `IntegerNumber`→`integer` nullable; `DecimalNumber`→`decimal(15,4)` nullable; `Textarea`→`text` nullable; `RichText`→`longText` nullable; `Date`/`Time`/`DateTime`→`date`/`time`/`dateTime` nullable; `ColorPicker`→`string(7)` nullable (hex); `Relation`→`unsignedBigInteger("{column}_id")` nullable, **with a real FK constraint added only when the target can be resolved to an existing table right now** (`resolveRelationTargetTable()`: another `Entity` that is itself already `is_installed` — looked up by slug — or a class from `config('entities.relatable_models')`, via `(new $class)->getTable()`); if the target isn't resolvable (e.g. relation points at an entity that isn't installed yet), the column is created anyway as a plain nullable id with no DB constraint, so install never fails because of relation ordering — it just skips the FK.
  - `EntitySchemaBuilder::RESERVED_COLUMN_NAMES` (`id`,`user_id`,`created_at`,`updated_at`,`deleted_at`) is the single source of truth for reserved names — `UpdateEntityBuilderRequest` (Phase 2) imports this constant rather than duplicating the list, and checks it against each field's **physical** column name (`"{column}_id"` for `Relation` fields, since that's the name that actually lands in the table — not the raw `column_name` the admin typed), likewise for entity-wide uniqueness. This was a real bug fixed while building this phase: a `Relation` field named `author` and a `String` field literally named `author_id` would otherwise both validate individually but collide once the table is actually created.
- `App\Services\EntityInstaller` — `install(Entity $entity)`: asserts the tree is complete (≥1 tab, every tab ≥1 card, every card ≥1 field — same structural rule as the builder, re-checked here since an entity's tree could theoretically still be incomplete at install time), then in one `DB::transaction()`: `EntitySchemaBuilder::create()`, four permissions via `JustAGate::createPermission()` (see naming below), `$entity->update(['is_installed' => true])`. `uninstall()`: no-op if not installed, throws if `is_system`, otherwise drops the table, deletes the four permissions (`JustAGate::findPermission()` + `deletePermission()`), flips `is_installed` back to false. Both throw plain `RuntimeException` with an Italian message on failure — `Admin\EntityController::install()`/`uninstall()` catch it and `back()->with('error', $e->getMessage())`, same "no dedicated exception classes" style as the rest of the app.
  - **Permission naming**: `entity_{slug}.index` / `.create` / `.edit` / `.delete` — deliberately namespaced `entity_{slug}` (underscore, not dot) so `RoleController::groupedPermissions()` (which buckets by `explode('.', $key)[0]`) groups each entity's four permissions together on the Roles→Permessi screen under its own heading, without colliding with the unrelated `entity.*` keys `Admin\EntityController`'s own actions get from the `acl` middleware (e.g. `entity.index` for `GET /admin/entities`).
  - **These four permissions are never checked by the `acl` middleware.** `AclCheck` derives its key from `Controller@action`, and every entity's records are served by the same single `EntityRecordController` — so the middleware can only ever produce a generic, entity-agnostic key from that controller, never `entity_contatti.index` specifically. Authorization for entity records is therefore done **by hand**, inside `EntityRecordController` itself (`request()->user()->cannot("entity_{$entity->slug}.index")`) and in the sidebar menu (`@can("entity_{$installedEntity->slug}.index")`) — the same manual-`@can` pattern the app already used for `admin.access` (see "layout & menus" above), now with a second real example.
- `App\Http\Controllers\EntityRecordController` (`app/Http/Controllers`, **not** under `Admin\`) — the generic frontend controller every installed entity's records go through, resolved via `{entity:slug}` route-model-binding (`Entity` doesn't override `getRouteKeyName()` globally — only this specific route customizes the binding column inline; admin routes still bind entities by numeric id). Currently just `index()` (view) + `data()` (`EloquentSource` JSON, columns limited to `id`/owner name/`created_at` — full per-field-type column rendering is Phase 5 work). Both actions call a shared `authorizeInstalledEntity()`: 404 (`NotFoundHttpException`) if `! $entity->is_installed` (no table to read), 403 (`abort(403)`) if the user lacks the `.index` permission. Routes live in `routes/web.php` inside the plain `auth` group (**not** `admin`-prefixed, **not** `acl`-middlewared, per the point above) — `entities/{entity:slug}/data` is registered before `entities/{entity:slug}` in the file for readability, though the two patterns don't actually overlap (different segment counts) so registration order isn't load-bearing here.
- `App\Models\EntityRecord` — the generic model behind every entity's records (no per-entity model classes). `EntityRecord::forEntity($entity)` does `(new static)->setTable($entity->table_name)`; this survives query hydration because `Model::newInstance()` (called internally whenever Eloquent builds a fresh model from a query result) copies `$this->getTable()` onto the new instance — confirmed by reading `vendor/laravel/framework/.../Model.php` directly, since this is the one part of the "dynamic table" pattern that's easy to get subtly wrong. `owner()` is a plain `belongsTo(User::class, 'user_id')`.
- **Sidebar menu**: `resources/views/layouts/base.blade.php` now queries `\App\Models\Entity::where('is_installed', true)->orderBy('name')->get()` directly in the Blade view (no view composer/controller involved — this shared layout is `@extend`-ed by every authenticated page, there's no single controller to inject the list from) and renders one `<li>` per entity the current user can see, gated by `@can("entity_{$installedEntity->slug}.index")`. Optional `icon` (a Tabler icon **class name**, e.g. `ti ti-users`, stored as a plain string on `entities.icon`) renders as `<i class="{{ $entity->icon }}">` — unlike the rest of the layout's menu icons, which are hand-inlined SVGs.

### per-role visibility levels (Phase 4)

- `entity_role_visibility` (Phase 1 table) gets its admin UI: `App\Http\Controllers\Admin\EntityVisibilityController` (`admin/entities/{entity}/visibility`, GET/PUT), a matrix of every non-admin `Role` × the 4 `EntityVisibilityLevel` cases as radio buttons, one level per role — same shape as `roles/permissions.blade.php`'s grouped-checkbox screen but radios instead of checkboxes (a role has exactly one level per entity, not a set). Admin roles (`is_admin=true`) are excluded from the list entirely — they always resolve to `Full` (see below), listing them would be misleading since selecting anything for them would have no effect, mirroring how the Roles→Permessi screen already refuses to render for the admin role.
- **Gotcha hit while building this**: `Illuminate\Database\Eloquent\Builder::pluck()` and `::value()` both hydrate a throwaway model and apply attribute casts whenever the column has one (confirmed by reading `Builder::pluck()`/`::value()` in `vendor/laravel/framework` directly) — so `EntityRoleVisibility::where(...)->pluck('level', 'role_id')` returns `EntityVisibilityLevel` **enum instances**, not raw strings, even though `pluck()`/`value()` look like they should bypass model hydration. `EntityVisibilityController::edit()` explicitly `->map(fn ($level) => $level->value)`s the plucked collection before handing it to the Blade view, specifically so `$currentLevel === $value` (comparing against a raw option-value string) works — comparing an enum instance to a string with `===` is always `false`. Any other code in this app that pluck()s/value()s a cast column needs the same treatment.
- `App\Services\EntityRecordAuthorizer` is the actual enforcement point — deliberately **not** part of Just A Gate (that package has no concept of row-level/ownership scoping at all, see the Phase 1/3 notes above). `levelFor(User, Entity)`: an `is_admin` role always short-circuits to `Full` (checked via `$user->getRoles()->contains('is_admin', true)`, the same trait method the layout menu already uses); otherwise every `EntityRoleVisibility` row for the user's roles on that entity is compared via `EntityVisibilityLevel::rank()` (0=OwnOnly … 3=Full) and the **highest-ranked** one wins — a user in two roles with different levels on the same entity gets the more permissive of the two, never the more restrictive. **A role with no row at all for a given entity defaults to `OwnOnly`** — the safe/restrictive default for a role nobody has explicitly opened up, not "no access" (that's still gated separately by the flat `entity_{slug}.index` permission from Phase 3) and not "full access" either.
  - `canView`/`canEdit`/`canDelete(User, Entity, int $ownerId)` — always `true` for one's own records (`$ownerId === $user->id`) regardless of level. Beyond that: `OwnOnly` never sees/touches others' records; `OwnManageOthersRead` can view others' but not edit/delete them; `OwnManageOthersEdit` can view **and edit** others' but still can't delete them; `Full` can do everything to everyone's records. This asymmetry (edit others allowed, delete others not, until the top level) is intentional per the original spec and encoded directly in the `match` arms — there's no configuration for it beyond picking one of the 4 fixed levels.
  - `scopeQuery(Builder, User, Entity)` — only `OwnOnly` actually filters the query (`where('user_id', $user->id)`); every other level returns the query untouched, since they can all at least *read* every record (the `canEdit`/`canDelete` split only matters once a user tries to act on a specific row, not for listing).
- `EntityRecordController::data()` now calls `$authorizer->scopeQuery($records, $request->user(), $entity)` before handing the query to `EloquentSource` — the datatable listing an `OwnOnly` user sees is already filtered server-side, not just hidden client-side.
- No route/controller yet enforces `canEdit`/`canDelete` on individual records — there's no edit/update/destroy action on `EntityRecordController` at all yet (Phase 5 adds those and is where those two methods actually get called per-row).

### frontend record CRUD (Phase 5)

- `App\Http\Controllers\EntityRecordController` (Phase 3's `index`/`data`-only stub) now has the full set: `create`/`store`/`edit`/`update`/`destroy`, all still on the single generic controller, all still manually authorized (`authorizeAction()` = flat `entity_{slug}.{action}` permission + 404 if not installed; `authorizeRow()` = `EntityRecordAuthorizer::canEdit()`/`canDelete()` against the specific row's `user_id`, only relevant for `edit`/`update`/`destroy` — `create` has no row yet, `index`/`data` are scoped via `scopeQuery()` instead of per-row checks). `edit(Entity $entity, int $record)`/`update(...)`/`destroy(...)` take a plain `int $record` route parameter, **not** route-model-bound — there's no single Eloquent model class per entity to bind against, so the controller resolves it itself via `findRecordOrFail()` (`EntityRecord::forEntity($entity)->newQuery()->findOrFail($id)`).
- **Validation is generated at request time from the entity's own field definitions** — `App\Http\Requests\StoreEntityRecordRequest::rules()` reads `$this->route('entity')->allFields()` and builds one rule set per field type (`Rule::in(array_keys($field->options))` for Select, `date_format:H:i` for Time, etc — see the file for the full type→rule map, it mirrors `EntitySchemaBuilder`'s type→column map one-to-one). `UpdateEntityRecordRequest` just `extends StoreEntityRecordRequest` with an empty body — create and update use identical rules here, unlike e.g. `Store/UpdateRoleRequest` where the slug-uniqueness rule differs between the two.
- **RichText sanitization happens in the controller, not the FormRequest** (`prepareAttributes()` → `sanitizeRichText()`) — `strip_tags($value, self::RICH_TEXT_ALLOWED_TAGS)` where `RICH_TEXT_ALLOWED_TAGS = '<b><i><u><strong><em><ul><ol><li><p><br><a>'`. This runs on every RichText field on every create/update, no opt-out. **`strip_tags()` only removes disallowed tags, not their inner text** — `<script>alert(1)</script>` becomes the plain text `alert(1)`, not an empty string; this is still safe against stored XSS (no executable tag survives) but don't expect stripped content to vanish, only its markup.
- **Checkbox fields are read straight from the request (`$request->boolean($column)`), not from `$validated`** — an unchecked HTML checkbox simply isn't submitted at all, so it would never appear in `$request->validated()` even with a `nullable` rule; `Request::boolean()` correctly defaults to `false` for an absent key, whereas indexing into `$validated[$column] ?? null` would just store `null`.
- **No per-entity/per-field model or migration exists for "which field displays as the row's label"** — Relation fields resolve a display label by falling back to *the target entity's first `String`-type field* (`relationLabels()`: `$target->allFields()->first(fn($f) => $f->type === EntityFieldType::String)`), or `"#{id}"` if the target has no String field at all. This is a heuristic, not a configured choice — a future "display field" setting on `Entity` would replace it if it turns out to matter once real system entities exist.
- **Relation `<select>` options and the records datatable's relation-column labels are computed with one query per Relation field, not per row** — `relationLabels(EntityField)` runs once per field and returns an `[id => label]` map, reused for every row/option; avoids an N+1 that would otherwise scale with row count.
- **The records index datatable's columns are generated from the entity's schema at render time** — `entities/index.blade.php` builds the Raccoon Tables `columns` array from `@json($entity->allFields()->map(...))`, one column per field (keyed by the field's physical column name, so Relation columns are `{column}_id`) plus the fixed `id`/`owner`/`created_at`/`actions` columns. The `actions` column's render callback reads **per-row `can_edit`/`can_delete` booleans that `EntityRecordController::data()` computes server-side** (via the same `EntityRecordAuthorizer` methods Phase 4 built) and only renders the Modifica/Elimina buttons when true — same pattern as the admin grids hiding buttons based on `is_system`/`is_installed`, just driven by per-row authorization instead of a static flag.
- **Generic value form** (`resources/views/entities/_form.blade.php`, shared by `create.blade.php`/`edit.blade.php`) renders `entity->tabs` as Bootstrap `nav-tabs`/`tab-content` (Tabler already bundles Bootstrap's `tab.js` via `tabler.min.js`, imported in `app.js` — no extra JS needed for tab switching itself) and, inside each tab, `.card`s per `EntityCard`, each field rendered by `entities/_field_input.blade.php` via a `@switch($field->type->value)`. Field names in this form are **flat physical column names** (`nome`, `stato`, `contatto_id`), not the bracketed/tokenized names the Phase 2 builder form uses — there's no repeater here, the set of fields is fixed and known at render time from the schema, so a plain form is enough.
  - Checkbox uses the standard "hidden `0` + real checkbox `1`, same `name`" trick so an unchecked box still submits something (though the controller ignores that value anyway and reads `$request->boolean()`, see above — the hidden input is there so a plain non-JS form still behaves sanely, and so `old()` repopulation after a validation error works for other fields on the same submit).
  - RichText renders a `contenteditable` `<div>` (not a `<textarea>`) plus a small `.btn-list` toolbar (bold `B`/italic `I`/underline `U`/`Elenco` for `insertUnorderedList`) and a `type="hidden"` companion input that actually gets submitted — `resources/js/entity-record-form.js` (new Vite entrypoint, same "own page-local `@vite()` call, not the shared layout head" pattern as `entity-builder.js`) wires the toolbar buttons to `document.execCommand(...)` (deliberately using the deprecated-but-still-universally-supported API rather than adding a WYSIWYG dependency, consistent with "don't change dependencies without approval") and, on `submit`, copies each `.rich-text-editor`'s `innerHTML` into its hidden input right before the browser serializes the form.
- Translations: `record-created`/`record-updated`/`record-deleted` status keys follow the same `@switch(session('status'))` pattern as every other admin/frontend CRUD screen in the app.

### import/export (Phase 6 — engine complete)

- `App\Services\EntitySchemaTransfer` — `export(Entity): array` walks `tabs.cards.fields` into a plain nested array (name/icon + tabs→cards→fields, **schema only, never record data**); `import(array): Entity` does the reverse, always producing a **new** `is_system=false, is_installed=false` entity (never overwrites an existing one, never re-installs anything — the admin installs it manually afterward like any custom entity, same as the plan intended). Both directions share the exact field shape `EntityBuilderController`/`UpdateEntityBuilderRequest` already use, so nothing new was invented here — an export is literally "what Phase 2 already persists," serialized.
- **`export()`'s return value must be plain arrays, not Eloquent collections** — the first implementation left `->values()` collections in place (no `->all()`/`->toArray()`), which is invisible when the payload only ever gets `response()->json()`'d (Laravel serializes collections to JSON arrays transparently) but breaks `import()` if called directly on that same in-memory structure (as the round-trip test does, to avoid a real JSON encode/decode in a unit-ish test): `is_array($collection)` is `false`, so `assertValidStructure()` rejected it as "no tabs." Fixed by chaining `->values()->all()` at every nesting level in `export()`. A reminder that "looks like an array when JSON-encoded" and "is actually a PHP array" are different guarantees, and code that consumes its own output directly (not just over HTTP) needs the real thing.
- **`import()`'s returned `Entity` must be `->refresh()`ed before handing it back** — `Entity::create([...])` deliberately omits `is_system`/`is_installed` (they should just take their migration defaults, `false`/`false`), but the in-memory model instance `create()` returns has those attributes **unset**, not `false` — Eloquent doesn't retroactively pull DB column defaults into an unsaved-then-saved instance's attribute bag. Casting an unset/null attribute through `EntityController`'s `boolean` casts yields `null`, not `false`. Since callers (the admin controller, tests) reasonably expect a freshly-created entity's boolean flags to already read correctly without an extra manual re-fetch, `import()` calls `$entity->refresh()` itself right before returning from its `DB::transaction()` closure. `EntityController::store()`/`update()` don't have this problem since their callers always re-fetch via `route()`-driven redirects to a fresh GET request.
- `assertValidStructure()` (private, called at the very top of `import()`, before the transaction even opens) re-implements the same reserved-column/entity-wide-uniqueness check `UpdateEntityBuilderRequest` has (see Phase 2/3 notes — both now read `EntitySchemaBuilder::RESERVED_COLUMN_NAMES`, so there's still only one source of truth for the reserved list itself), plus basic shape checks (name present, ≥1 tab, every tab has ≥1 card, every card has ≥1 field, every field's `type` is a real `EntityFieldType` value via `EntityFieldType::tryFrom()`). Throws plain `RuntimeException` on the first problem found, same style as `EntityInstaller`'s own validation — and, crucially, `import()` validates **before** the `DB::transaction()` even opens, so a malformed file never creates a partial `Entity`.
- `App\Http\Controllers\Admin\EntityController::export()`/`importForm()`/`import()` are thin wrappers around the service: `export()` returns `response()->json($transfer->export($entity))->header('Content-Disposition', 'attachment; filename="entity-{slug}.json"')` (a same-origin JSON download, not a separate file-storage round trip — nothing is ever written to disk); `import()` `json_decode()`s the uploaded file's raw contents, bails with a flashed `error` on invalid JSON (`json_decode` returning non-array) before ever touching the service, then delegates to `EntitySchemaTransfer::import()` inside a `try/catch (RuntimeException)`, same pattern as `install()`/`uninstall()`.
- Routes: `admin/entities/import` (GET form / POST handle, names `admin.entities.import.form`/`admin.entities.import`) and `admin/entities/{entity}/export` (GET, `admin.entities.export`) — registered alongside the other custom `entities/*` sub-routes, before `Route::resource('entities', ...)`, though as with the earlier phases none of these literal-segment routes actually collide with the resource's wildcard routes (different segment counts/literals), so registration order here is for readability, not correctness.
- Index page gets an "Importa" button (next to "Nuova entità") and each row gets an "Esporta" link (a plain `<a href>` to the GET export route — no JS/form needed, the browser just downloads/opens the JSON response) in the Raccoon Tables `actions` render callback, alongside the existing Modifica/Progetta/Visibilità/Installa-Disinstalla/Elimina controls.

**This closes the Entity builder engine** (Phases 1–6): metadata design → real table + permissions on install → per-role ownership scoping → generic frontend CRUD → schema portability. Defining the actual **system entities** (what they are, their fields, seeding them at install time) is explicitly the next, separate piece of work — see the "Fuori scope" section of the original plan.

### Codice field type (post-engine addition)

- 13th `EntityFieldType` case: `Code = 'code'`, label "Codice". New `EntityFieldType::isGenerated(): bool` (true only for `Code`) is the single check everything else keys off to treat this type specially — never validated as user input, never editable, never touched on update.
- **No new dedicated columns on `entity_fields` for the prefix** — it's stored inside the existing `options` JSON column as `{"prefix": "INV-"}`, reusing the same column Select already uses for its choice list (just a different shape depending on `type`). What *is* new: `entity_fields.sequence` (unsignedInteger, default 1, migration `2026_07_11_185937_add_sequence_to_entity_fields_table.php`) — the atomic counter, one per Code field (not per entity — two Code fields on the same entity have fully independent sequences).
- `App\Services\EntityCodeGenerator::nextValue(EntityField $field): string` — the only place that reads/increments `sequence`. Runs inside `DB::transaction()` with `EntityField::where('id', ...)->lockForUpdate()` on the read, so concurrent record creation can't hand out the same number twice. Returns `"{$prefix}{$currentSequence}"`, **no zero-padding** (client's explicit choice — `INV-1`, `INV-2`, ... `INV-10`, not `INV-00001`).
- `EntitySchemaBuilder`: `Code` → `string(255)` nullable, identical column shape to `String` — the "generated, not user-typed" distinction is entirely an application-layer concept, not a DB-schema one.
- `EntityRecordController::prepareAttributes()` gained a `bool $generateCodes` parameter (`true` only from `store()`, defaults `false`) — for each field where `$field->type->isGenerated()`, either calls `$this->codeGenerator->nextValue($field)` (create) or skips the field entirely, leaving it out of the `$attributes` array so `update()` never overwrites an existing record's code with `null`. `StoreEntityRecordRequest::rules()` skips generated fields entirely (`continue` before `rulesFor()`), so **a `code` value submitted by the client is silently ignored**, not merely unvalidated — it's never read from `$validated` in the first place.
- Builder UI: `_field.blade.php` gained a `.field-code-group` (a single "Prefisso" text input, submitted as `[code_prefix]`, distinct request key from Select's `[options]` textarea so both can coexist in the DOM without one clobbering the other) shown only when `type=code`, toggled by the same `syncFieldVisibility()` in `entity-builder.js` that already handled `.field-options-group`/`.field-relation-group`. `EntityBuilderController::parseOptions()` branches on `type === 'code'` first (before the existing Select branch) and returns `['prefix' => $trimmed]` or `null` if left blank — prefix is optional, a bare incrementing number is valid.
- Record value form (`entities/_field_input.blade.php`): a `code` field renders **no input at all** — a read-only `<input readonly>` showing the already-generated value when editing an existing record, or an italic hint ("Verrà generato automaticamente al salvataggio.") with no form control when creating a new one. This is presentation only; the real guarantee that the value can't be tampered with is server-side (previous bullet), not this read-only attribute.

### Builder drag-and-drop + resizable fields (post-engine addition)

- **First third-party JS dependency in the app**: `sortablejs` (`npm install sortablejs`, `package.json`'s `dependencies`), imported as an ES module (`import Sortable from 'sortablejs'`) at the top of `resources/js/entity-builder.js`. Everything else the app has (Tabler, Raccoon Tables) was already there before this — this is the first time a new npm package was added specifically to support one feature, and it was an explicit client choice (asked directly: SortableJS vs. hand-rolled HTML5 Drag & Drop) rather than a default.
- **Scope is deliberately same-parent-only**: tabs reorder among tabs, cards reorder within their own tab, fields reorder (and resize) within their own card — **no cross-card or cross-tab dragging**. This was a scope decision made during planning, not a technical limitation of SortableJS (which supports cross-list dragging via its `group` option trivially) — the blocker is that every input's `name` attribute hardcodes its tab/card token in the path (`tabs[t3][cards][c7][fields][f2][name]`, see Phase 2), so moving a field's DOM node to a different card would silently break its submitted data unless every name attribute in its subtree got rewritten on drop. Not implemented because it wasn't asked for; if cross-container moves are wanted later, that name-rewriting is the piece to add.
- **Reordering needed zero backend changes** — position was already derived from DOM/array submission order in `EntityBuilderController::update()` since Phase 2 (`array_values($request->input('tabs', []))`, etc.). SortableJS's only job is to actually move the DOM nodes; the existing save logic does the rest for free. Each sortable list gets its own `Sortable.create(container, {handle: '...', animation: 150})`: one for `#tabs-container` (handle `.tab-drag-handle`), one **per tab** for its `.cards-container` (handle `.card-drag-handle`), one **per card** for its `.fields-container` (handle `.field-drag-handle`). New tabs/cards/fields added via the existing `addTab()`/`addCard()`/`addField()` template-cloning functions (Phase 2) get their own container wired up immediately after insertion (`wireTab()`/`wireCard()` in `entity-builder.js`) — a freshly-added container isn't sortable until this runs.
- **Drag handles, not whole-row dragging**: each tab/card/field row has a small `⠿` button (`.tab-drag-handle`/`.card-drag-handle`/`.field-drag-handle`, `cursor: move`) that Sortable's `handle` option restricts dragging to — without this, trying to drag by clicking inside a text input or the "Rimuovi" button would fight with normal interaction (text selection, button clicks) instead of triggering a drag.
- **New `entity_fields.width` column** (unsignedTinyInteger, default 12, migration `2026_07_11_190605_add_width_to_entity_fields_table.php`) — a Bootstrap column-span (1–12), same grid system the rest of the app already uses (`row row-cards`, `col-md-*`). Validated server-side (`UpdateEntityBuilderRequest`: `between:1,12`) **and** defensively clamped again in `EntityBuilderController::update()` (`min(12, max(1, (int) ($fieldInput['width'] ?? 12)))`) — the clamp is currently unreachable through the validated path (an out-of-range value gets rejected by the FormRequest before the controller ever runs) but is cheap insurance against a future caller that bypasses validation.
- **Resizing is NOT SortableJS** — Sortable only reorders; the resize handle (`.field-resize-handle`, an 8px-wide invisible strip pinned to a field-item's right edge via `position: absolute`) is a small hand-rolled `mousedown`/`mousemove`/`mouseup` interaction in `entity-builder.js`. On `mousedown` it records the starting mouse X, the field's current `width` (read from `data-width`), and a "column step" in pixels (`fieldsContainer.getBoundingClientRect().width / 12`); on every `mousemove` while active it computes `Math.round(deltaX / step)`, adds it to the starting width, clamps to 1–12, and swaps the field-item's `col-md-N` class + updates its hidden `[width]` input + `data-width` live. There's no separate "drop" step — the class/hidden-input state IS the persisted state, submitted as-is with the rest of the form.
- **The builder's field-item box itself now resizes to `col-md-{width}`** (it lives inside its card's `.fields-container`, which is a Bootstrap `.row`) — so narrowing a field in the builder visually shows it sitting side-by-side with siblings exactly as it will on the real record form. This forced a layout rewrite of `admin/entities/_field.blade.php`: the old internal `row`/`col-md-3` grid (name/column/type/required side-by-side) had to become a simple vertical stack (each setting `mb-2`, full width of whatever the outer box's current width is) — nesting a 4-across grid inside a box that can itself be as narrow as 1/12 of the card would make the inner inputs unusably cramped.
- **Record value form respects the same `width`**: `entities/_form.blade.php` wraps each card's fields in a `.row`, and `entities/_field_input.blade.php`'s outer wrapper changed from a plain `mb-3` to `col-md-{{ $field->width }} mb-3` — multiple narrow fields (e.g. two `width=6` fields) now sit on the same line automatically, purely via Bootstrap's grid math; no JS "does this fit on the row" calculation exists or is needed.
- **Testing a real native HTML5 drag through headless Chrome/Selenium is unreliable** (well-known Dusk/Selenium limitation, not new to this app — see the `confirm()` dialog gotchas earlier in this doc for a similar "headless Chrome behaves differently" class of issue). Rather than fight that, `entity-builder.js` exposes `window.__entityBuilderSetFieldWidth(fieldEl, width)` purely for test automation, and `tests/Browser/Admin/EntityBuilderDragDropTest.php` exercises the **outcome** a real drag/resize would produce — directly reordering DOM nodes and calling the exposed setter via `$browser->script(...)` — then submits the form and asserts the persisted `position`/`width` in the database. This tests everything downstream of the drag gesture (DOM state → submit → persistence) without needing to simulate the gesture itself.

### Builder redesigned as a live WYSIWYG preview (post-engine addition, replaces the first drag-and-drop pass)

The client found the first drag-and-drop builder (settings-panel-style field boxes, an 8px resize sliver, tabs stacked as bordered sections rather than real tabs) confusing — fields always looked full-width and the resize handle wasn't discoverable. The builder was rebuilt to **render as close as possible to the eventual record form** (client's explicit directive), with structural metadata entry (naming a tab/card, configuring a field) moved into modals so the canvas itself stays a clean preview.

- **Second explicit npm dependency**: `bootstrap` (`^5.3.7`) was added to `package.json`'s `dependencies` — but this is not really a *new* library on the page: `@tabler/core` already depends on and bundles Bootstrap 5.3.7 (Tabler is built on top of it; `data-bs-toggle` attributes for dropdowns/tabs already worked everywhere before this), and the package was already physically present in `node_modules` as a transitive dependency. What's new is `entity-builder.js` now **imports it directly** (`import { Modal } from 'bootstrap'`) to drive modals programmatically, rather than relying only on `data-bs-*` auto-init — so it was made an explicit top-level dependency for correctness (deterministic `npm ci`), not installed fresh. No `npm install bootstrap` was needed; `npm install` after the `package.json` edit resolved to the already-present version.
- **Tabs are now real Bootstrap nav-tabs**, split across two containers that used to be one: `resources/views/admin/entities/_tab_nav.blade.php` (new — the `<li>` in `#tabs-nav`: drag handle, the actual tab-switch button `data-bs-toggle="tab"`, a rename (✎) button) and `admin/entities/_tab.blade.php` (repurposed — now renders only the `.tab-pane` content: a `row row-cards` of card columns, an "Aggiungi card" button, a "Rimuovi tab" button). **The tab's `name` hidden input lives in the nav `<li>`, not the pane** — this is load-bearing, not cosmetic: `EntityBuilderController::update()` still derives `position` from `array_values($request->input('tabs', []))`, and PHP builds that array using each `tabs[TOKEN]` key's *first appearance* in the submitted field order. Since the nav `<ul>` is rendered (and thus submits its fields) before `#tabs-content`, dragging the nav `<li>`s (via `Sortable.create('#tabs-nav', ...)`) is what actually controls submitted tab order — reordering the on-screen tab-content panes was deliberately **not** implemented, it isn't needed for correctness and would just be extra bookkeeping. Cards and fields didn't need this split: each is still a single DOM node holding its own name/settings, so dragging the node directly reorders it correctly, same as originally built.
- **Cards render as real Tabler `.card` boxes** (`admin/entities/_card.blade.php`, rewritten) in a `col-md-6` column — a card-header with drag handle + title + rename/remove buttons, a card-body containing the fields grid. This is structurally identical to how `entities/_form.blade.php` (the real record form) already rendered cards since Phase 5 — the builder now matches it directly instead of approximating it.
- **Fields are placeholder boxes, not inline settings panels.** `admin/entities/_field.blade.php` was rewritten from a full settings form (name/column/type/required/options all visible and stacked) to a small clickable preview box (`.field-preview`, shows just the field's name + type label) sized to `col-md-{width}` — **all** the actual settings (name, column, type, required, Select options, Code prefix, Relation target, default value) now live as **hidden inputs** on the field's wrapper div (`.field-name-input`, `.field-column-input`, `.field-type-input`, etc.) and are edited through a single shared `#field-modal` (in `builder.blade.php`), opened by clicking the placeholder. This is why the resize handle is now much easier to grab/see: a compact placeholder box narrowing in front of you is an obvious, discoverable resize target, unlike a tall multi-input settings panel that never visually "looked" resizable even when its `col-md-N` class was correctly applied.
- **One shared `#name-modal`** (a single text input) is reused for four different actions — create-tab, rename-tab, create-card, rename-card — distinguished purely by which JS closure (`onSave` callback) is currently assigned to it (`openNameModal(title, initialValue, onSave)` in `entity-builder.js`); there's exactly one Bootstrap `Modal` instance for it, not one per action. Same singleton pattern for `#field-modal` (one instance, `currentFieldEl` tracks which field-item's hidden inputs to read from / write back to on save).
- **A newly-added field opens its edit modal immediately** (`addField()` calls `openFieldModalFor(fieldEl)` right after inserting the placeholder) — there's no "blank unlabeled placeholder sitting on the canvas until the admin figures out to click it" state.
- **`<fieldset disabled>` no longer fully locks an installed entity's builder page** on its own, now that settings entry happens via click-driven modals instead of native `<input>`/`<select>` elements (`disabled` on a `<fieldset>` only disables real form controls, not click handlers on plain `<div>`s/buttons). `entity-builder.js` now checks `form.dataset.installed === '1'` (set from `$entity->is_installed` in `builder.blade.php`) as its very first statement and returns immediately, skipping **all** wiring — Sortable, modals, resize — for an installed entity, rather than relying on the fieldset alone.
- Dusk coverage updated for the new flow: `tests/Browser/Admin/EntitiesTest.php` now drives the real modal sequence (open "Aggiungi tab" → wait for `[data-testid="name-modal-input"]` → type → click `[data-testid="name-modal-save"]` → `waitUntilMissing('.modal-backdrop')`, same pattern repeated for the card and field modals) instead of typing into inline inputs. `tests/Browser/Admin/EntityBuilderDragDropTest.php` (resize/reorder) needed **no changes** — it already worked by manipulating `.field-item`/`.fields-container` DOM nodes and calling `window.__entityBuilderSetFieldWidth` directly via `$browser->script(...)`, and those hooks/classes were preserved through the rewrite.

### Builder polish: full-width cards, a real resize handle, button spacing (post-engine addition)

Follow-up client feedback on the WYSIWYG builder redesign above: cards should always be full-width, the resize interaction wasn't discoverable/working, and the rename/remove icon buttons looked cramped.

- **Cards are always `col-12`** now (`admin/entities/_card.blade.php`), not `col-md-6` — one card per visual row in the builder, matching what the client wants the eventual record form to look like.
- **Resize handle rebuilt to actually be grabbable and visible.** It moved from a bare, unstyled 10px `position:absolute` sliver sitting as a *sibling* of `.field-preview` (at the outer `.field-item` column's edge, inside the Bootstrap grid gutter padding) to a *child* of `.field-preview` itself (`position: relative` on `.field-preview`, handle absolutely positioned within it) — this puts the grab target exactly at the edge of the box the user actually sees, not at an invisible offset a few pixels further out inside the column gutter. It's now 14px wide with real CSS (a `<style>` block scoped to `builder.blade.php` — the app's first inline `<style>` block anywhere, justified here because this is bespoke interactive-builder chrome with no Tabler/Bootstrap equivalent to reuse): a subtle shaded gradient strip with a small grip line (`::after`), highlighting on `:hover` and while actively dragging (`.is-resizing` class, toggled by `entity-builder.js` on `mousedown`/`mouseup`).
- **`columnStep()` was measuring the wrong element.** It divided `.fields-container` (the Bootstrap `.row`)'s own `getBoundingClientRect().width` by 12 — but a `.row` has negative left/right margins (to offset its `.col-*` children's gutter padding), making its own bounding box measurably *wider* than the visible column area. That overestimated the pixel distance needed to cross one column step, making drags feel unresponsive/require more movement than expected. Fixed to measure `.fields-container.parentElement` (the `.card-body`) instead — the actual visual width the 12 columns fill.

## Global search (top navbar, main app section only)

- `App\Http\Controllers\GlobalSearchController::search()` — a single `GET /search` (`route('search')`) endpoint in the plain `auth` group (not `admin`-prefixed). Loops every `Entity::where('is_installed', true)`, keeps only those the user passes `can("entity_{slug}.index")` on, then for each one filters `allFields()` down to text-like types (`String`/`Textarea`/`RichText`) and `orWhere($column, 'like', ...)`s across them (with `%`/`_`/`\` escaped by hand — no Laravel helper for that). **Both authorization layers used elsewhere for entity records are reused here**, not reimplemented: the flat `entity_{slug}.index` permission (Just A Gate) gates which entities are searched at all, and `EntityRecordAuthorizer::scopeQuery()` (Phase 4, see above) row-scopes each entity's query the same way the records grid does — an `OwnOnly` user searching never finds another user's record here either. Returns JSON grouped per entity (`{results: [{entity: {slug, name}, records: [{id, title, url}]}]}`), capped at 5 records/entity, `title` taken from the entity's first `String` field (same "pick the first String field as the label" convention `EntityRecordController::relationLabels()` already used for relation `<select>`s) falling back to `"#{id}"`, `url` via `route('entities.edit', [$entity, $record->id])`. A query under 2 characters short-circuits to `{results: []}` without touching the DB.
- Front-end lives in `layouts/app.blade.php`'s `<header>`, wrapped in `@unless(request()->routeIs('admin.*'))` — **this is the only mechanism gating "main app section, not admin"**, there's no explicit Blade section flag; every `admin.*`-named route (the whole `Route::prefix('admin')->name('admin.')` group in `routes/web.php`) hides it, everything else (dashboard, settings, entity record pages) shows it. The input's `data-url` attribute holds `route('search')` (URL generated server-side, not hardcoded in JS) and the results `<div class="dropdown-menu">`'s `data-no-results` attribute holds the translated empty-state string — both read by the JS in `resources/js/app.js` rather than duplicating `t()` calls client-side.
- The JS (`resources/js/app.js`, bottom) debounces input (250ms, 2-char minimum), fetches `data-url`, and renders one `dropdown-header` + N `dropdown-item` links per entity group, toggling the results `<div>`'s Bootstrap `show` class exactly like the sidebar's `raccoon-layouts` dropdown and admin-menu search already do elsewhere in this file (`classList.add/remove('show')`, not inline `style.display` — see the raccoon-layouts theming work above for why). A `requestId` counter discards stale responses that resolve out of order (e.g. a fast keystroke followed by a slow one that returns first).

## Tom Select (every real `<select>` in the app, always — no vanilla selects)

- **Hard rule going forward: prefer the JS plugins the Tabler template itself ships over plain vanilla form fields.** The first application of this is `<select>` → Tom Select, applied to every plain-HTML `<select>` this app renders (there is no opt-out markup — the standing rule is "always"). Tom Select isn't a separate npm dependency: `@tabler/core` vendors a full copy of it at `node_modules/@tabler/core/dist/libs/tom-select` (JS: `dist/js/tom-select.complete.js`, a UMD build Vite's commonjs interop resolves to a default export same as `@tabler/core/dist/js/tabler.min.js` already was; CSS: `dist/css/tom-select.bootstrap5.min.css`, plus Tabler's own override layer at `@tabler/core/dist/css/tabler-vendors.min.css` — both imported in `resources/css/app.css`). This scope is deliberately bounded to `<select>` elements in **this app's own Blade views** — it does not reach into `raccoon-tables`' own grid-internal filter-bar dropdowns (third-party library-rendered markup, not ours to convert).
- **`resources/js/tom-select.js`** is the shared wrapper, imported once (side-effect import) in `app.js` so it's available on every page: `tomSelect(target, options)` (wraps one `<select>`, guarded against double-init via Tom Select's own `el.tomselect` instance reference; defaults include `maxOptions: null` — Tom Select's own default is `50`, which silently truncated the icon picker's dropdown to the first 50 of ~5,100 icons and looked exactly like "not all icons are shown"), `tomSelectAll(root = document)` (wraps every `<select>` under `root` **except ones carrying `data-tom-select-manual`**; called once on `DOMContentLoaded` to auto-convert everything present at page load — this is *why* no per-element opt-in markup is needed for the common case, every plain `<select>` this app renders gets the treatment automatically), and `setSelectValue(target, value, silent = true)`. All three are also assigned to `window.*` for the app's many plain (non-module) inline `<script>` blocks that can't `import` them (same pattern as `window.icon`, above).
- **`data-tom-select-manual`** is the escape hatch for a `<select>` that needs custom Tom Select options (e.g. a custom `render.option`/`render.item`, see the entity icon picker below) — `tomSelectAll()` skips it, and the Blade partial that owns it calls `window.tomSelect('#id', {...})` itself. **Gotcha that cost real debugging time**: that manual call must be wrapped in its own `document.addEventListener('DOMContentLoaded', ...)`, same as `tomSelectAll()` itself is. A plain classic (non-`type="module"`) inline `<script>` block runs synchronously *during* HTML parsing — before `app.js` (a deferred `type="module"` script) has executed and assigned `window.tomSelect` — so calling `window.tomSelect(...)` unwrapped at the top level of such a block throws `TypeError: window.tomSelect is not a function` in the console and silently no-ops the whole select (caught via Selenium's browser-log capture in a Dusk test, not visible without checking the console explicitly).
- **Why `setSelectValue()` has to exist**: Tom Select hides the original `<select>` (`display: none`) and renders its own UI reading from its *own* internal state — reading `.value` off the original (now-hidden) element still works transparently (Tom Select keeps it mirrored, and dispatches a real `change` event on it for user-driven selections, so existing `addEventListener('change', ...)` code and native form submission both kept working unchanged everywhere in this app without modification). But *writing* `element.value = x` only updates the hidden original element — Tom Select's visible custom UI does not observe that assignment and silently drifts out of sync. `setSelectValue()` is the one correct way to programmatically set a select's value regardless of whether it's wrapped (`el.tomselect ? el.tomselect.setValue(value, silent) : el.value = value`), silent by default to match plain `el.value = x`'s no-event semantics (pass `silent: false` to fire one deliberately).
- **Two call sites needed fixing to stay correct under Tom Select**, both were "set `.value` on a select programmatically" spots that predate this conversion:
  - `resources/js/entity-builder.js`'s `openFieldModalFor()` — re-populating the field-type/relation-target selects when reopening the modal to *edit* an existing field. `document.getElementById('field-modal-type').value = type` → `window.setSelectValue('#field-modal-type', type)` (same for `#field-modal-relation`). Without this, reopening the modal for an existing field would show the correct value in the hidden select (so saving still worked) but the *visible* Tom Select control would keep showing the previous/placeholder text — a real, easy-to-miss bug.
  - The `raccoon-layouts` dropdown override (`resources/views/vendor/raccoon-layouts/dropdown.blade.php`) — its `buildOptions()` rebuilds the whole option list from scratch on every `raccoon-layouts:*` event (saved, saved-as, renamed, copied, default-set, deleted). Previously did this via raw DOM (`select.remove(1)` in a loop, `document.createElement('option')` + `appendChild`, bare `select.value = x`). Rewritten to detect `select.tomselect` and, when present, use `ts.removeOption(value)` (iterating `Object.keys(ts.options)`, skipping the empty placeholder), `ts.addOption({value, text})`, `ts.refreshOptions(false)` to re-render the dropdown, and `setSelectValue()` for the final selection — falls back to the original raw-DOM path when `tomselect` isn't present (defensive; in practice it always is by the time any `raccoon-layouts:*` event fires, since those only ever happen well after `DOMContentLoaded`'s auto-init has run). The per-`<option>` `dataset.isPublic`/`dataset.isDefault` attributes from the old raw-DOM version were dropped in the rewrite — grepped first and confirmed nothing in the app ever read them, and Tom Select doesn't render real `<option>` elements for its own UI anyway (only bothers keeping the hidden native select's `<option>` list in sync for form-submission purposes), so preserving them had no value.
- **The entity icon `<select>` (see below) is the one place a custom `render.option`/`render.item` matters** — see the entity icon picker section for the per-option `<img>` preview built on top of this.
- **Known cost, accepted**: Tom Select is not virtual-scrolled by default, so a `<select>` with thousands of options (the icon picker, ~5,100 entries) renders that many `<div class="option">` nodes into the dropdown on first open (now that `maxOptions: null` actually lets all of them render, see above). Typing into the control's search box does filter what's *visible*, but doesn't reduce the DOM node count up front. Not addressed — no complaint about it yet, and doing so would mean reaching for Tom Select's `virtual_scroll` plugin, a separate scope from "convert selects to Tom Select".

## Icons (Tabler Icons, always inline SVG — never the webfont)

- **Hard rule going forward: never load the Tabler icon webfont.** Every icon is printed as its actual inline `<svg>...</svg>` markup, via one of two helpers that both read from the same source of truth — the `@tabler/icons` npm package's static SVG files (`node_modules/@tabler/icons/icons/{variant}/{name}.svg`, `config('icons.path')`, `variant` is `outline` or `filled`, default `outline` per `config('icons.default_variant')`).
- **PHP/Blade**: `icon(string $name, ?string $variant = null): string` (`app/helpers.php`, autoloaded like `t()`/`preferences()`). Reads the file straight off disk, in-process `static`-cached by `"{variant}/{name}"`. Both `$name` and `$variant` are passed through `basename()` before touching the filesystem — a caller can never escape the icons directory (e.g. `icon('../../../../etc/passwd')` just returns `''`, not an error). An unknown icon returns `''`, not an exception — icons render inline in markup, where a missing file should silently degrade to "no icon". Usage: `{!! icon('search') !!}` (unescaped — it's real markup, not text).
- **JS**: `icon(name, variant = 'outline')` (`resources/js/icon.js`), exported and also assigned to `window.icon` in `app.js` for the many plain (non-module) inline `<script>` blocks in this app (raccoon-layouts dropdown, sidebar/global search wiring, etc.) that can't `import` it. **Deliberately does not bundle SVGs at build time** — an earlier `import.meta.glob(...)` attempt that lazily imported every file under `node_modules/@tabler/icons/icons/*/*.svg` technically worked, but registering ~6,000 dynamic-import entries in Vite's module graph bloated `app.js` itself from ~208 KB to ~1 MB and produced 6,164 output chunks (~29 MB in `public/build`) even though no icon was ever eagerly loaded — the *lookup table* alone was the cost, not the actual icon payloads. Reverted in favor of an HTTP round-trip instead: the JS helper is `async`, `fetch()`s `` `${window.ICONS_BASE_URL}/${variant}/${name}` `` (`ICONS_BASE_URL` set once in `layouts/app.blade.php`'s `<script>window.CSRF_TOKEN = ...` block, alongside the CSRF token, via `@json(url('/tabler-icons'))` — not hardcoded in JS, same reasoning as the global-search `data-url` attribute above) and caches the **pending promise** per `"{variant}/{name}"` key in a module-level `Map`, so concurrent calls for the same icon share one request instead of firing duplicates.
- **`App\Http\Controllers\IconController::show(string $variant, string $name)`** is the HTTP-accessible twin the JS helper calls — `GET /tabler-icons/{variant}/{name}` (`route('icons.show')`, inside the plain `auth` group like every other route in this app, not left open — kept consistent with "everything requires login" even though the SVGs themselves aren't sensitive). Just calls the same `icon()` PHP helper and either 404s (`$svg === ''`) or returns the raw SVG with `Content-Type: image/svg+xml` and a `public, max-age=31536000, immutable` `Cache-Control` (safe: these files never change without a `composer`/`npm` dependency bump, which busts the URL's browser cache anyway since... actually it doesn't bust the URL, there's no version/hash in the path — a stale browser cache after upgrading `@tabler/icons` is a known, accepted tradeoff for now, not handled). The route also has a regex `where()` constraint (`variant` = `[a-z]+`, `name` = `[a-z0-9-]+`) as a second, independent layer of path-traversal defense on top of the helper's own `basename()` — a request like `/tabler-icons/outline/..%2F..%2Fetc%2Fpasswd` 404s at the **router** level, never reaches the controller.
- **`/icons/...` (not `/tabler-icons/...`) was the original path and is why this feature looked completely broken for a while** despite every automated test (Feature + Dusk, headless Chrome via `php artisan serve`) passing: this app's real dev vhost runs behind **Apache**, and stock Arch Linux `httpd` ships `/etc/httpd/conf/extra/httpd-autoindex.conf` with a server-wide `Alias /icons/ "/usr/share/httpd/icons/"` (the classic FancyIndexing directory-listing icons) — an `Alias` is resolved before any vhost's `DocumentRoot`/`.htaccess`/`mod_rewrite`, so **every** request under `/icons/...`, on **every** vhost on that Apache instance, resolved straight to that filesystem path and 404'd from Apache itself, never reaching `index.php`/Laravel at all. Confirmed via `tail /var/log/httpd/asgardcrm_error.log`: `AH00128: File does not exist: /usr/share/httpd/icons/outline/building`. `php artisan serve` (used for all Dusk runs during development) has no such alias, which is exactly why it never reproduced there. **Lesson: a route path that looks generic/short is a namespace collision risk against the web server itself, not just against this app's own routes** — moved to `/tabler-icons/...`, deliberately specific enough not to collide with anything Apache/nginx ship by default.
- **New npm dependency**: `@tabler/icons` (`^3.44.0`) added to `package.json`'s `dependencies` (not `devDependencies` — both the PHP and JS helpers need the SVG files to exist on disk/be servable at actual runtime, not just at build time, so this isn't a build-only tool). Composer's `setup` script already runs `npm install` before `npm run build`, so `node_modules/@tabler/icons` is guaranteed present in this app's normal install flow.
- **Several of the app's pre-existing hand-copied inline SVGs were retrofitted** to call `icon()`: the sidebar-menu-search and global-search magnifying-glass icons (`icon('search')`, both were literally `search.svg`'s markup already, just hand-copied), the notifications bell (`icon('bell')`), and every `nav-link-icon` in both sidebar menus — `layouts/admin.blade.php` (`icon('user')`/`icon('users-group')`/`icon('replace')`/`icon('language')`/`icon('database')` for Utenti/Ruoli/Traduzioni/Lingue/Entità) and `layouts/base.blade.php` (`icon('gauge')` for Dashboard, `icon('settings-cog')` for the Amministrazione link — these two replaced bespoke hand-drawn shapes that didn't exactly match any real Tabler icon, so the swap is a deliberate icon *change*, not a byte-for-byte one, chosen to fit each link's meaning). **One was deliberately left untouched**: the breadcrumb home icon (`layouts/app.blade.php`) has an extra `icon-1` sizing class baked into its hand-written markup that plain `icon('home')` output doesn't include (swapping it would shrink-regress that one icon's size — the helper has no class-injection feature).
- **`layouts/base.blade.php`'s per-entity sidebar link now also renders `$installedEntity->icon` via `icon()`** instead of the old `<i class="{{ $installedEntity->icon }}"></i>` webfont pattern — see the entity icon picker below for where that column's values come from.

### Entity icon picker (admin/entities/_form.blade.php)

- **`icon_names(?string $variant = null): array`** (`app/helpers.php`, same file/pattern as `icon()`) — every icon name available for a variant (default `outline`), sorted, extension-stripped, via `glob(config('icons.path')."/{$variant}/*.svg")`, `static`-cached per variant. Backs the entity form's icon `<select>`: **~5,100 `<option>`s, one per real file on disk** — deliberately not curated down to a shortlist, per the literal ask ("una select con tutte le icone disponibili"). It's a real `<select>` in the Blade markup, converted to Tom Select **with `data-tom-select-manual`** (it needs a custom `render`, so it opts out of `tomSelectAll()`'s blanket auto-init and initializes itself, see the Tom Select section above) — the search box Tom Select provides is what makes ~5,100 options actually navigable; a plain native `<select>` was the original (now superseded) implementation, and briefly a *default*-initialized Tom Select was too (silently truncated to 50 options by Tom Select's own `maxOptions` default — see above).
- **Preview is per-option, inline in the dropdown itself, not a separate box** — per explicit client feedback that a separate "current selection" preview span "doesn't work" (in hindsight, likely never actually broken — see below — but a per-option preview is a strictly better UX for browsing 5,100 icons regardless, so the separate `#icon-preview` span was removed rather than debugged further). `admin/entities/_form.blade.php`'s inline `<script>` passes a custom `render: { option: fn, item: fn }` to `window.tomSelect('#icon', {...})` — the same `renderIconOption(data, escape)` function is used for both the dropdown list (`render.option`) and the closed control's own display (`render.item`), each producing `<img src="{ICONS_BASE_URL}/{variant}/{value}" width="20" height="20" loading="lazy"> <span>{name}</span>`. **Uses `<img>` against `IconController` (see the Icons section below), not the JS `icon()` fetch-and-inline-SVG helper** — deliberately: `icon()` is designed for "one icon, inlined as real markup"; using it here would mean an `await fetch()` round-trip *per rendered option* (up to ~5,100 of them) before the dropdown could render anything. An `<img>` tag lets the browser's own native image loading/caching handle that instead (each icon is still served by the same `IconController` endpoint, still cached a year via `Cache-Control: immutable`), so `render.option` returns synchronously with a `<img>` tag whose `src` browsers fetch independently and lazily (`loading="lazy"`).
- **Layout**: name and icon fields share one Bootstrap `.row` — `name` in `.col-md-8`, `icon` in `.col-md-4`. The (edit-only) read-only slug field stays full-width below the row, unchanged.
- **Validation tightened accordingly**: `StoreEntityRequest`/`UpdateEntityRequest`'s `icon` rule changed from `['nullable', 'string', 'max:100']` (any string, including the old free-text webfont-class convention like `"ti ti-users"`) to `['nullable', Rule::in(icon_names())]` — now that the field is a controlled `<select>`, only a name that resolves to a real file is accepted; a stale/garbage value fails validation instead of silently rendering nothing via `icon()`'s empty-string fallback.

- **New composer dependency**: `fazzinipierluigi/laraccoon-layouts` (`^1.0`, actual resolved `1.0.3`) — a companion package to `raccoon-tables`/`laraccoon_datasource` from the same author, letting a user save/name/share/set-default **column layouts** (order, width, hidden, pinned — see `raccoon-tables`' own `getLayout()`/`setLayout()` in its `DOCUMENTATION.md` §15) per grid. **Naming inconsistency worth remembering**: unlike `laraccoon_datasource` (Composer name uses an underscore, matching its GitHub repo `laraccoon_datasource`), this one's Composer name uses a **hyphen** (`laraccoon-layouts`) even though its GitHub repo is `laraccoon_layouts` — verified directly against Packagist before installing, because an AI-summarized fetch of the repo's raw README had gotten this detail wrong (also GitHub-repo hyphen instead of underscore risk generally: never trust a webfetch summary in isolation for a package name — install and read the real vendor source instead, which is exactly what happened here).
- **Setup performed**: `composer require fazzinipierluigi/laraccoon-layouts`, then `php artisan vendor:publish --tag=raccoon-layouts-config` and `--tag=raccoon-layouts-migrations` (published migration was dated `2024_01_01_...` by the package — renamed to `2026_07_12_000000_create_raccoon_layouts_table.php` purely for filename consistency with the rest of this app's migrations; ordering was never actually at risk since `0001_01_01_...create_users_table` already sorts before both `2024` and `2026`, and the layouts table's `user_id` FK needs `users` to exist first). `config/raccoon_layouts.php`: only changed `'locale'` from the package default `'en'` to `'it'` (this app's default locale) — `middleware` (`['web','auth']`), `user_model` (`App\Models\User::class`), `route_prefix` (`raccoon-layouts`) were already correct defaults, no reason to override.
- **`<meta name="csrf-token">` didn't exist anywhere in the app before this** — the app's own JS only ever needed `window.CSRF_TOKEN` (set in `layouts/app.blade.php`, used by every admin grid's row-action delete forms). The layouts package's own `scripts.blade.php` reads the token exclusively via `document.querySelector('meta[name="csrf-token"]')`, so a `<meta name="csrf-token" content="{{ csrf_token() }}">` tag was added to `layouts/app.blade.php`'s `<head>` — now the *second* CSRF delivery mechanism on every page, kept alongside `window.CSRF_TOKEN` rather than migrating everything to one, since changing the existing one risked touching every admin grid's delete-form JS for no benefit.
- **The package's own JS (`RaccoonLayouts.save()`/`saveAs()`/`load()`) calls bare global functions `getLayout()`/`setLayout()`, not methods on any specific grid instance** — since a page only ever has one grid, `resources/js/app.js` gained a shared `window.wireRaccoonLayouts(grid)` helper (called once, right after `grid.render(...)`, from every grid-owning view) that closes over that page's `grid` and defines `window.getLayout`/`window.setLayout`/`window.resetLayout` (the third one — restoring the grid's initial layout — is what the dropdown's blank "— Standard —" placeholder option calls). Every grid page now follows the same four-line pattern: `@raccoonLayoutsDropdown` above the grid card, `var grid = new window.RaccoonGrid(...).render(...)`, `window.wireRaccoonLayouts(grid);` right after, and `@raccoonLayoutsScripts` at the very end of `@section('content')`.
- **Known limitation carried over from `raccoon-tables` itself, not introduced by wiring this package in**: `setLayout()` "is client-side only — server mode ignores sort/filter restoration since those are managed by the server" (verbatim from `raccoon-tables`' own docs §15). Every grid in this app is server-side (`serverAdapter`), so **loading a saved layout restores column order/width/visibility, but not the sort or filters that were active when it was saved**. This isn't worked around — it's an accepted, documented gap.
- **Where the dropdown was placed**: a small `d-flex justify-content-end` bar directly above each grid's `.card`, not inside `@section('buttons')` (that slot is for the page's primary create/action buttons, and layout management is a per-grid tool, not a page-level action).

### Per-column filters (`filterBar: true`) — enabled everywhere, with care taken where server support was missing

`raccoon-tables`' filter bar and `filterLookup` (dropdown filter, exact-match, ideal for foreign keys — see its `DOCUMENTATION.md` §7 "Lookup Filter") were **already fully implemented** on both sides before this change: the npm package's `Filter.ts` mixin client-side, and `Fazzinipierluigi\LaraccoonDatasource\EloquentSource::applyFilters()` server-side (every `FilterSign` operator from the npm package's `SERVER-API.md` — `=`,`!=`,`==`,`!==`,`>`,`<`,`a_`,`_a`,`regex`,`empty`,`!empty`,`+`,`-`,`in`,`T`,`F` — was already handled in `vendor/fazzinipierluigi/laraccoon_datasource/src/EloquentSource.php`). This section only had to *turn the feature on per grid* and be careful about columns that aren't real, directly-filterable DB columns.

- **`filterBar: true`** added to every grid's config: `admin/users`, `admin/roles`, `admin/translations`, `admin/entities`, and the per-installed-entity `entities/{slug}` records grid. `admin/languages` was **not** touched — it has no `RaccoonGrid` at all (a plain server-rendered table, see the "admin CRUD" section above), so there's no grid to add a filter bar to.
- **Columns backed by a computed/joined value (not a real queryable DB column) got `sortable: false, filterable: false` explicitly** — filtering/sorting on these would otherwise generate a broken SQL query server-side (`EloquentSource` just does `WHERE {index} ...`/`ORDER BY {index}` against whatever string the column's `index` is, with no awareness that it doesn't exist as a column):
  - `admin/users`: the `roles` column (`$user->roles->pluck('name')->join(', ')` — a joined multi-value string, not a single FK).
  - `admin/roles`: `permissions_count` (a relation `count()` computed in the row-mapping callback, not selected in the base query) — **this was actually a pre-existing latent bug**: `sortable` defaults to `true` on every `ColumnDef` unless set otherwise, so clicking to sort by "Permessi" would already have thrown a SQL error before this change; fixed alongside adding `filterable: false` since it's the same column.
  - `entities/{slug}` (entity records): the `owner` column (record owner's `name`, joined via the `owner()` relation, not a column on the entity's own dynamic table).
  - Every grid's `created_at` column got `filterable: false` (kept `sortable: true`, which is fine — sorting a real datetime column works correctly): the **displayed** value is always a pre-formatted `'d/m/Y H:i'` string, but a text-filter's `LIKE` comparison runs server-side against the **raw** stored datetime value, so a user typing what they see on screen (e.g. `11/07/2026`) would silently never match anything. Rather than ship a filter box that looks like it should work and doesn't, it's disabled — a real correctness call, not just caution for its own sake.
- **`admin/translations`' grid needed real server support added, not just a config flag** — `TranslationController::data()` doesn't use `EloquentSource` at all (it hand-builds the pivoted `{data, total}` response, see the "admin CRUD" section above), so it never read the `filters` request param. A new private `TranslationController::applyKeyFilter()` was added — reads and JSON-decodes `filters` the same way `EloquentSource` does, but only recognizes a filter on the one real, non-pivoted column (`key`), mapping the same handful of `FilterSign`s (`==`, `!==`, `!=`, `a_`, `_a`, default `=`) that column can meaningfully support. The per-language pivoted columns (`it`, `en`, …) already had `filterable: false` set since they were first built (Phase-era `TranslationSeeder`/pivot work) — they still can't be filtered, for the same "not a real single column" reason as everywhere else.
- **`type: 'boolean'` was adopted for every real boolean column** (`roles.is_system`, `entities.is_system`, `entities.is_installed`, and entity records' `Checkbox`-type fields) — this gets `raccoon-tables`' automatic True/False/Null filter dropdown *and* automatic disabled-checkbox cell rendering for free, replacing hand-written `render: function(params) { return params.value ? 'Sì' : 'No' }` callbacks that existed purely to translate a raw boolean into display text. **This required a real behavior change for entity-record Checkbox fields**: `EntityRecordController::displayValue()` used to convert a Checkbox field's value to a translated `t('Sì')`/`t('No')` **string** for the grid response — that string isn't a boolean, so it would have broken `type: 'boolean'`'s auto-renderer (which expects a real `true`/`false`). Changed to `(bool) $value` — the raw value — and let `raccoon-tables` render it. No existing test asserted the old `'Sì'`/`'No'` string (checked via grep before changing), so this was a safe, contained swap.
- **Relation and Select entity fields get `filterLookup`, per the client's explicit ask ("se la colonna è una relazione, il filtro deve essere una lookup")**: `EntityRecordController` gained `relationLookupsForColumns(Entity $entity): array` — for every `Relation` field, reuses the already-existing `relationLabels()` (built for the create/edit forms' `<select>`s, see Phase 5 notes above) and reshapes it into `raccoon-tables`' `filterLookup.options` shape (`[{value, name}]`), keyed by the field's physical column (`{column}_id`). This is passed from `index()` to the view as `relationLookups`, and `entities/index.blade.php`'s `@php` block builds each field's full column definition server-side (`type`, `filterLookup`) before handing the array to `@json(...)` — **`Select` fields also get `filterLookup`** (not explicitly requested, but a natural, low-risk extension: they already have a fixed, small `entity_fields.options` choice list in exactly the shape a lookup dropdown wants — same treatment, no new query needed since the options are already loaded on the field). `IntegerNumber`/`DecimalNumber` fields get `type: 'number'` (numeric `>`/`<` filter operators). `Date`/`DateTime` fields were **deliberately left as plain `string` filtering** rather than given `type: 'date'`/`'datetime'` — `EntityRecord` has no `$casts` for its dynamic columns, so `raccoon-tables` would receive the raw DB-driver date/datetime string (`"2026-07-11"` / `"2026-07-11 15:30:00"`) for its own `type: 'date'` cell renderer and date-picker filter to `new Date(...)`-parse; a non-`T`-separated datetime string's parseability is not reliably specified across browsers (works in Chrome/V8, historically inconsistent in Safari), and this app has no existing precedent of shipping raw MySQL datetime strings through a JS `Date` parser — rather than introduce a possible cross-browser display bug, the safer, contained choice was to skip it. Revisit if/when `EntityRecord` gains real date casts.

## known non-obvious gotchas (chronological)

1. SQLite `dropColumn` on a uniquely-indexed column requires `dropUnique` first (see migration above).
2. Pint can silently break `tests/Pest.php` if it reorders `use` past a `pest()->extend()` call — always keep imports at the top of that file, re-check after running Pint on it.
3. Dusk cannot use `:memory:` SQLite — must be a real file, shared between the test process and the served app process via a matching `.env`.
4. `php artisan serve` and the Dusk test-runner process are separate PHP processes started at different times — any env swap must happen *before* starting `serve`, not just before running `dusk`.
5. Laravel's `@can`/`can:` middleware and Just A Gate's `@can` Blade directive are NOT the same mechanism here — see "layout & menus" above. Using Laravel's `can:` middleware with a Just A Gate key always denies.
6. `Role::syncPermissions()` takes permission **keys**, not ids (unlike `User::syncRoles()`, which does accept ids) — see "admin CRUD" above.
7. Raccoon Tables' `serverAdapter` defaults to POST; our GET-only data routes need `method: 'GET'` set explicitly in every grid config, or requests 405.
8. `EloquentSource::apply()` silently returns zero rows if the request has no `limit` param — always pass `start`/`limit` when hitting a `*/data` endpoint directly (tests included).
9. Headless Chrome (`--headless=new`) resolves a `confirm()` dialog **injected into the DOM via JavaScript** (e.g. Raccoon Tables' `render()` callback HTML, not present in the server's initial response) immediately — Dusk's `waitForDialog()`/`acceptDialog()` will time out waiting for something that already resolved; just wait for the resulting page change instead. **This does NOT generalize to every `confirm()`**: a `confirm()` on a form present in the page from the very first server-rendered response (e.g. `admin/languages/index.blade.php`'s delete button, no JS grid involved) genuinely blocks and *does* need explicit `->waitForDialog()->acceptDialog()` — see gotcha #14.
10. **Tailwind CSS and Bootstrap/Tabler both define a class literally named `.collapse`, with opposite meanings, and Tailwind's wins.** Tailwind ships a `visibility` utility `.collapse { visibility: collapse }` (table-row visibility helper); Bootstrap/Tabler use `.collapse` for collapsible sections (`.collapse:not(.show) { display: none }`, overridden to `display:flex!important` at the `lg` breakpoint for `.navbar-vertical`). With both stylesheets loaded, `display` ends up correct (Tabler's `!important` wins) but `visibility: collapse` from Tailwind is never contested — the element takes up layout space but renders with all descendants invisible. This is exactly what happened to the sidebar menu (`#sidebar-menu.navbar-collapse.collapse`): content existed in the DOM, `assertPresent()` passed, but nothing was visible to a real user. Root cause was `resources/css/app.css` importing both `@import 'tailwindcss'` and `@import '@tabler/core/dist/css/tabler.min.css'`. Fix: don't import Tailwind at all — this project uses Tabler/Bootstrap exclusively, never Tailwind utility classes. **Any Dusk assertion for on-screen navigation must use `assertVisible()`, not `assertPresent()`** — presence-only checks do not catch visibility bugs like this one (that's exactly how this bug shipped past the original test suite).
11. `roles.slug` only had a plain (non-unique) index in the vendor migration — two `slug=admin` rows actually coexisted in this project's dev DB at one point. Fixed with an app migration adding a real `unique('slug')` constraint; see "role-specific rules" above.
12. `Translation::upsert()` (and any other query-builder bulk write) doesn't fire Eloquent's `saved`/`deleted` events, so it doesn't trigger `Translation::forgetCache()` on its own — callers must call it explicitly. See "translations" above.
13. `Translation::$cache` (static, in-process) survives across all test cases in one Pest/PHPUnit process and can leak stale values between unrelated tests; reset it globally via `afterEach()` in `tests/Pest.php`. Same file also defines `seedLanguages()` — call it in any test touching translations/preferences views, since the `languages` table starts empty under `RefreshDatabase`/`DatabaseMigrations` and nothing seeds it automatically.
14. Blade's `@json(...)` directive can fail to parse a complex inline expression (e.g. `$collection->map(fn ($x) => [...])` directly inside the parens) with `Unclosed '[' does not match ')'` — compute the value in a preceding `@php` block into a variable first, then `@json($variable)`. Also: a `confirm()` present in the page's initial server-rendered HTML (not injected later via JS) genuinely blocks Dusk and needs `->waitForDialog()->acceptDialog()`, unlike the JS-grid-injected ones described in gotcha #9.
